# اجرای اپلیکیشن Node.js

Runner مربوط به Node.js فرایند یک اپلیکیشن را از داخل کارت همان اپ در **اپلیکیشن‌ها** مدیریت می‌کند. از releaseهای موجود و ترجیح Runtime همان اپ استفاده می‌کند؛ اپ یا پنل جداگانه‌ای نمی‌سازد. پروژه‌های npm، pnpm و Yarn Classic با lockfile پشتیبانی‌شده و یک اسکریپت Runtime معتبر یا entry point پشتیبانی‌شدهٔ Next.js/Nuxt قابل اجرا هستند.

## پیش از اولین استقرار

۱. در **اپلیکیشن‌ها** یک اپ بساز یا کارت موجود را باز کن و چارچوب آن را **Node.js** بگذار.
۲. نسخهٔ Node زمان اجرا و در صورت نیاز نسخهٔ جداگانهٔ build را در **مدیریت Runtime** انتخاب کن. باینری دقیق باید از قبل روی همین VPS نصب باشد.
۳. یک پورت آزاد بزرگ‌تر از ۱۰۲۳ برای اپ رزرو کن. Runner انتظار دارد برنامه از `PORT` استفاده کند و فقط روی `127.0.0.1` گوش بدهد؛ قرار نیست پردازش مستقیم روی رابط عمومی شبکه باز شود.
۴. سورس را با `package.json` معتبر و دقیقاً یک lockfile پشتیبانی‌شده مستقر کن. به‌صورت پیش‌فرض `scripts.start` و در صورت وجود `scripts.build` انتخاب می‌شود؛ از بخش **Runtime و ابزارها** می‌توان نام اسکریپت دیگری را از manifest انتخاب کرد.

برای نمونه، manifest ساده می‌تواند `"scripts": {"build":"tsc -p .", "start":"node dist/server.js"}` داشته باشد. این فقط مثال است؛ ARG فایل پروژه را می‌خواند و اسکریپت خود پروژه را در محیط محدود اجرا می‌کند. وجود Node به‌تنهایی ثابت نمی‌کند که پروژه یک وب‌سرور است.

## بررسی پروژه و مدیر بسته

با بازکردن **مدیریت** در کارت اپ، وضعیت Runner خوانده می‌شود. بازرسی release جاری، نسخهٔ Node، شرط `engines.node`، مدیر بسته، نام اسکریپت‌ها، آماده‌بودن وابستگی‌ها و فقط **نام** متغیرهای محیط را نشان می‌دهد. مقدار محیط هیچ‌وقت از API برنمی‌گردد.

مدیر بسته از روی lockfile انتخاب می‌شود:

| فایل قفل | فرمان |
| --- | --- |
| `package-lock.json` | `npm ci --no-audit --no-fund` |
| `pnpm-lock.yaml` | `pnpm install --frozen-lockfile` |
| `yarn.lock` با Yarn Classic | `yarn install --frozen-lockfile` |

اگر چند lockfile هم‌زمان باشد یا `packageManager` مدیر پشتیبانی‌نشده‌ای مثل Yarn Berry را درخواست کند، بازرسی خطای روشن می‌دهد. ARG مدیر دیگری را بی‌صدا انتخاب یا lockfile را بازتولید نمی‌کند. مدیر بسته باید از مخازن APT تنظیم‌شدهٔ میزبان نصب شده باشد. اسکریپت‌های lifecycle هنگام نصب فقط در sandbox اجرا می‌شوند؛ بعضی وابستگی‌های native بدون این اسکریپت‌ها نصب نمی‌شوند. محیط build به دیتابیس ARG، کلید TLS و تنظیمات سیستم دسترسی ندارد.

## رفتار Deploy

برای اپ Node، استقرار این مراحل را انجام می‌دهد:

۱. سورس Git، ZIP یا پوشهٔ مجاز را با محدودیت‌های Job بررسی و دریافت می‌کند. اگر همهٔ فایل‌های ZIP زیر یک پوشهٔ مشترک باشند، ARG فقط همان پوشهٔ wrapper را حذف می‌کند تا `package.json` در ریشهٔ release قرار بگیرد. ZIPهای دارای چند ریشه بدون تغییر ساختار می‌مانند.
۲. پوشهٔ پایدار اپ و فایل خصوصی محیط را در صورت نیاز می‌سازد.
۳. `package.json` را بررسی، مدیر بسته را از lockfile تعیین و وابستگی‌ها را نصب می‌کند؛ اسکریپت Build تنظیم‌شده اجرا می‌شود. مقدار `auto` اسکریپت `build` را در صورت وجود انتخاب می‌کند و `none` آن را برای SSR رد می‌کند. انتشار Static حتماً به Build نیاز دارد.
۴. نصب و build در unit موقت systemd با DynamicUser، فضای موقت خصوصی، مسیرهای سیستمی فقط‌خواندنی، سقف CPU، RAM، تعداد task، خروجی و حداکثر ۲۰ دقیقه اجرا می‌شود.
۵. release را اعتبارسنجی و `current` را اتمی جابه‌جا می‌کند. سرویس release را با bind فقط‌خواندنی می‌بیند.
۶. اگر سرویس Node از قبل فعال باشد، آن را restart و listener روی loopback و مسیر Health Check تنظیم‌شده (پیش‌فرض `/`) را آزمایش می‌کند. فقط پاسخ HTTP از نوع 2xx پذیرفته می‌شود. در شکست فعال‌سازی یا سلامت، ARG تلاش می‌کند release قبلی را برگرداند و سرویس قبلی را دوباره اجرا کند. اپ متوقف‌شده خودکار روشن نمی‌شود.

حجم خروجی build محدود است و الگوهای متداول رمز از آن پاک می‌شوند. تغییر مرحله‌ها و خروجی محدود فرمان‌ها در SQLite ذخیره می‌شوند؛ هنگام فعال‌بودن Job، پنل وضعیت را تازه می‌کند و لاگ بعد از refresh صفحه باقی می‌ماند. برای هر Job حداکثر ۲۰۰۰ رخداد اخیر نگه‌داری و در UI صفحه‌بندی می‌شود. خروجی پس از پایان هر فرمان package ثبت می‌شود؛ حین اجرای فرمان، نشانگر مرحلهٔ جاری نمایش داده می‌شود و stream بایت‌به‌بایت نیست. build همچنان ممکن است به‌علت دسترسی شبکه، وابستگی native نصب‌نشده، ناسازگاری نسخهٔ Node یا اسکریپت خود پروژه شکست بخورد. موفقیت همهٔ مخزن‌ها روی همهٔ میزبان‌ها تضمین نمی‌شود.

تنظیم‌های **Build script**، **Runtime script** و **Health Check path** در بخش Runner قرار دارند. فیلد اسکریپت فقط نام یکی از scriptهای `package.json` را می‌پذیرد و فرمان shell آزاد نیست. مسیر Health Check یک مسیر محلی HTTP است که از خود VPS روی loopback بررسی می‌شود؛ مانند `/health` یا `/ready` که پاسخ 2xx بدهد.

## متغیرهای محیط

فرم **متغیرهای Runtime** می‌تواند کلید/مقدار معتبر اضافه یا جایگزین کند. فرم فقط نام کلیدهای ذخیره‌شده را نشان می‌دهد. مقدار خالی یعنی مقدار فعلی حفظ شود؛ مرورگر راهی برای خواندن secret قبلی ندارد. فایل خصوصی `.env` در پوشهٔ shared استقرار قرار دارد و به releaseها متصل می‌شود. سرویس systemd آن را در namespace خود فقط‌خواندنی می‌خواند. برنامه فقط در `shared/data` اجازهٔ نوشتن دارد؛ release و فایل محیط هنگام اجرا فقط‌خواندنی‌اند.

این فرم تنظیمات زمان اجرا را تغییر می‌دهد، نه build-time را. اگر bundler فرانت‌اند مقدار دیگری هنگام build لازم دارد، دوباره Deploy کن. ذخیرهٔ مقدارها آن‌ها را در رویداد Audit یا لاگ سرویس چاپ نمی‌کند.

## کنترل سرویس و Reverse Proxy

بعد از استقرار موفق **فعال‌سازی سرویس** را بزن. ARG برای هر اپ یک unit ثابت systemd می‌سازد که نامش از UUID اپ مشتق شده است. سرویس از `DynamicUser`، فایل‌سیستم محدود، `HOST` روی loopback، پورت رزروشده، `Restart=on-failure`، مهلت ۳۰ ثانیه برای توقف تمیز و سقف ثابت منابع استفاده می‌کند. فرم هیچ فرمان shell یا unit دلخواه نمی‌پذیرد.

اگر اپ دامنه دارد، ARG می‌تواند سایت reverse proxy مستقل و مدیریت‌شدهٔ خودش را در Nginx بسازد. سایت نامرتبط یا سایتی که دامنه/پورتش از تنظیم تولیدشده تغییر کرده باشد بازنویسی نمی‌شود. پیش از موفقیت، تنظیم Nginx اعتبارسنجی و reload می‌شود. Headerهای WebSocket و timeoutهای proxy هم تنظیم می‌شوند. صدور SSL و انتقال HTTP به HTTPS همچنان از صفحهٔ Nginx انجام می‌شود؛ Runner بی‌اجازه گواهی نمی‌گیرد. اگر دامنه ثبت نشده باشد، سرویس محلی مدیریت می‌شود اما مسیر عمومی ساخته نمی‌شود.

وضعیت سرویس از systemd و socket واقعی خوانده می‌شود. پیش از اعلام موفقیت، ARG بررسی می‌کند پورت فقط روی loopback گوش کند و سپس Health Check تنظیم‌شده را می‌فرستد. پاسخ غیر 2xx، پاسخ نامعتبر، bind عمومی یا نبود listener باعث شکست بررسی و توقف سرویس تازه‌فعال‌شده می‌شود. **نمایش لاگ‌های اجرا** خروجی اخیر و محدود سرویس را می‌خواند و shell باز نمی‌کند.

## عملیات و محدودیت‌ها

- **مدیریت / تازه‌سازی:** وضعیت را هنگام درخواست می‌خواند؛ وقتی کارت بسته است فایل‌ها را مکرر اسکن نمی‌کند.
- **فعال‌سازی / توقف:** فقط unit متعلق به همان اپ و ARG را تغییر می‌دهد. پورت متعارض یا release نامعتبر مانع فعال‌سازی می‌شود.
- **نمایش لاگ‌های اجرا:** لاگ اخیر سرویس را می‌خواند و ترمینال ایجاد نمی‌کند.
- **ذخیرهٔ متغیرهای محیط:** نام و مقدار را بررسی و فایل خصوصی را به‌روز می‌کند؛ مقدار ذخیره‌شده قابل بازخوانی نیست.
- **Deploy / Retry / بازگشت:** از Job پایدار و تاریخچهٔ release استفاده می‌کند. Rollback کد را عوض و سرویس فعال را restart می‌کند؛ migration دیتابیس یا اثر خارجی کد اپ را برنمی‌گرداند.
- **دستورهای سفارشی پیش از فعال‌سازی:** در فرم Deploy، هر خط یک فرمان مستقل است و بعد از دریافت منبع و نصب/Build خودکار، اما پیش از فعال‌کردن release اجرا می‌شود. آرگومان‌ها به فرایند داده می‌شوند؛ shell، pipe، redirect و expansion اجرا نمی‌شود. Runner فقط release موقت و cache را در sandbox با سقف CPU/RAM/زمان می‌بیند؛ `.env` تولید و رازهای سرویس به آن داده نمی‌شوند. رمز یا توکن را در آرگومان ننویس. خروجی زنده هر دستور در جزئیات همان Job ثبت می‌شود و اگر کد خروج غیرصفر باشد فعال‌سازی متوقف می‌شود. اثرهای بیرونی، مثل تغییر دیتابیس، با rollback فایل‌ها خنثی نمی‌شوند.
- **تنظیمات Runtime:** نام اسکریپت‌های manifest و مسیر Health Check را انتخاب می‌کند. ذخیره، فرمان دلخواه اجرا نمی‌کند؛ برای بازتولید امن unit فعال از **اعمال تنظیمات سرویس** استفاده کن.

ARG مدیریت Node cluster، انتقال staging، نصب خودکار package manager یا تفسیر shell آزاد را پشتیبانی نمی‌کند. نام اسکریپت Build و Runtime از فهرست `package.json` انتخاب می‌شود؛ فرمان سفارشی فقط به شکل یک برنامه و آرگومان‌های آن اجرا می‌شود. برای انتشار Static React/Vite و SSR با Next.js/Nuxt، راهنمای انتشار Static و SSR را ببین.

## عیب‌یابی

| خطا یا نشانه | بررسی |
| --- | --- |
| `package.json` یا نقطهٔ شروع برنامه پیدا نشد | ZIP می‌تواند یک پوشهٔ ریشهٔ مشترک داشته باشد؛ ARG آن را در صورت ساختار یکنواخت برمی‌دارد. ZIPهای چندریشه‌ای بدون تغییر می‌مانند. یک اسکریپت start یا entry point پشتیبانی‌شدهٔ Next/Nuxt تعریف کن. |
| lockfile گم، متعارض یا پشتیبانی‌نشده است | یک lockfile پشتیبانی‌شده را نگه دار و commit کن. Yarn Berry هنوز پشتیبانی نمی‌شود. |
| Runtime یا مدیر بسته موجود نیست | نسخهٔ دقیق را از Runtime Manager نصب و inventory را تازه کن. |
| build شکست خورد | خروجی Job را ببین؛ شرط engine، نیاز build native و اسکریپت پروژه را بررسی کن. |
| Job در صف می‌ماند یا خطای پایگاه‌داده می‌دهد | از کارت Job گزینهٔ «مشاهدهٔ جزئیات فرایند» را باز کن. خطای SQLite با متن اصلی و لاگ Worker نمایش داده می‌شود؛ Worker هنگام خطای موقت دوباره تلاش می‌کند و خطا در گزارش Job ثبت می‌ماند. خروجی واقعی Git و نصب/Build Node هم زنده و صفحه‌بندی‌شده ذخیره می‌شود. |
| پورت اشغال است | پورت آزاد رزرو کن و برنامه را برای استفاده از `PORT` تنظیم کن؛ bind عمومی نکن. |
| listener loopback نیست یا Health Check پاسخ 2xx نمی‌دهد | اسکریپت Runtime، مسیر Health Check، لاگ‌ها، متغیرهای لازم و رعایت `HOST` و `PORT` را بررسی کن. |
| Nginx proxy رد شد | `server_name` و تنظیم سایت موجود را ببین؛ ARG سایت دستی‌تغییریافته یا نامرتبط را جایگزین نمی‌کند. |
| پس از فعال‌سازی ناموفق سرویس خاموش شد | Runner برای شکست بررسی، سرویس تازه‌ساخته را متوقف کرده است؛ علت را اصلاح و دوباره فعال کن. |

## API و مجوز

Runner از `GET /api/apps/{id}/node`، `GET|PUT /api/apps/{id}/node/service`، `GET|PUT /api/apps/{id}/node/runtime-settings`، `PUT /api/apps/{id}/node/environment` و `GET /api/apps/{id}/node/service/logs` استفاده می‌کند. لاگ Deploy از `GET /api/deploy/jobs/{id}/logs?tail=true&limit=500` برای آخرین صفحه، `?after={id}` برای لاگ تازه و `?before={id}` برای صفحهٔ قدیمی‌تر دریافت می‌شود. Write به نشست مدیر، Origin معتبر، مالکیت اپ روی سرور انتخاب‌شده و رویداد Audit نیاز دارد. عملیات ریشه از طریق درخواست ساختاریافته روی helper محافظت‌شده انجام می‌شوند؛ رشتهٔ shell دریافتی از کاربر اجرا نمی‌شود.

تست خودکار انتخاب manifest و lockfile، اعتبارسنجی محیط، محدودیت unit، بررسی loopback، پاسخ HTTP و مسیرهای rollback را می‌پوشاند. اجرای سرویس روی VPS آزمایشی Debian/Ubuntu با systemd و Nginx هنوز تست یکپارچگی لازم دارد و در نتایج تست مخزن ادعا نشده است.
