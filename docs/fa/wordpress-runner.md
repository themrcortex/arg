# استقرار اولیهٔ مدیریت‌شدهٔ WordPress

قالب **WordPress** می‌تواند یک سایت تازه را روی VPS محلی بسازد و منتشر کند. این یک جریان نصب اولیهٔ مدیریت‌شده است؛ ثبت دستی اپلیکیشنی با چارچوب `wordpress` به‌تنهایی آن را فعال نمی‌کند.

## پیش‌نیازها

- از قالب WordPress استفاده کن و hostname معتبر، عنوان سایت، نام کاربری مدیر، ایمیل و گذرواژهٔ ۱۲ تا ۱۲۸ نویسه‌ای بده.
- سرور باید به مخزن بسته‌ها و منبع WordPress دسترسی خروجی داشته باشد. ARG با مدیر بستهٔ سیستم Nginx، در صورت نبود MariaDB، MariaDB، PHP-FPM/CLI و افزونه‌های PHP موردنیاز را نصب می‌کند؛ ارتقای عمومی بسته‌های سیستم اجرا نمی‌شود.
- privileged helper و `setfacl` باید موجود باشند. مسیر معمول انتشار ARG برابر `/var/lib/arg/deployments` است؛ والد مسیر سفارشی باید از قبل برای کاربر `www-data` قابل‌عبور باشد.
- برای صدور خودکار Let’s Encrypt، DNS عمومی باید به همین VPS برسد. شکست DNS یا ACME نصب سالم HTTP را حذف نمی‌کند و به‌صورت هشدار در Job می‌ماند.

## کارهایی که استقرار اول انجام می‌دهد

1. نسخهٔ دقیق انتخاب‌شده را از منبع رسمی WordPress می‌گیرد و فایل‌های هسته و نسخه را اعتبارسنجی می‌کند.
2. بسته‌های محدود Runtime را نصب/بررسی می‌کند و Nginx، PHP-FPM و MariaDB را فعال می‌کند.
3. دیتابیس و حساب MariaDB مختص همین اپ را می‌سازد. اگر دیتابیس از قبل نشان مالکیت ARG را نداشته باشد، آن را تصاحب نمی‌کند.
4. `wp-config.php` با مالکیت root و دسترسی خواندن PHP-FPM می‌سازد. اعتبار دیتابیس و فرم مدیر اولیه در secret vault رمز‌شدهٔ root نگهداری می‌شوند؛ پس از نصب موفق، Secret فرم مدیر پاک می‌شود.
5. `wp-content` را بیرون از release نگه می‌دارد تا آپلودها پس از استقرار مجدد باقی بمانند. دسترسی لازم PHP-FPM به همان اپ محدود است. ACL روی `/var/lib/arg` فقط اجازهٔ عبور (`execute`) به `www-data` می‌دهد و امکان فهرست‌کردن پوشه را نمی‌دهد.
6. سایت مدیریت‌شدهٔ Nginx را می‌سازد و فعال می‌کند، برای SSL تلاش می‌کند، فقط پس از سلامت TLS آدرس WordPress را به HTTPS می‌برد و در پایان مسیر `/wp-login.php` را از Nginx و PHP-FPM بررسی می‌کند. Job فقط پس از پاسخ واقعی HTTP 200 موفق می‌شود.

هر مرحله در Job استقرار با نام‌های `wordpress-runtime`، `wordpress-database`، `wordpress-ssl` و `wordpress-health` ثبت می‌شود. جزئیات Job خروجی واقعی هر مرحله و پیام نهایی بازیابی را نشان می‌دهد.

## SSL و دسترسی عمومی

تلاش SSL از ایمیل قالب و اتصال Certbot/Nginx استفاده می‌کند. صرف صف‌شدن Job تضمین صدور گواهی نیست؛ DNS، دسترسی بیرونی پورت ۸۰، محدودیت ACME و اعتبارسنجی ارائه‌دهنده باید موفق شوند. اگر صدور شکست بخورد ولی بررسی محلی Nginx موفق باشد، سایت با HTTP می‌ماند و هشدار در Job حفظ می‌شود. DNS و دسترسی فایروال Nginx را بررسی کن و سپس از تب دامنه و SSL همان سایت صدور را انجام بده.

Health Check محلی ثابت می‌کند VPS مسیر ورود WordPress را از طریق Nginx/PHP-FPM خودش سرو می‌کند؛ DNS عمومی، دسترسی فایروال یا اعتبار TLS از بیرون را ثابت نمی‌کند. این موارد را از یک کلاینت خارج از VPS جداگانه بررسی کن.

## امنیت و بازیابی

- فقط مدیر می‌تواند فرم نصب اولیه را ارسال کند. helper فقط عملیات مشخص WordPress را می‌پذیرد و shell عمومی root نیست.
- سایت با کاربر `www-data` اجرا می‌شود؛ کاربر پنل ARG برای Runtime سایت استفاده نمی‌شود.
- شناسه‌های دیتابیس از UUID اپ ساخته می‌شوند. ورودی SQL اعتبارسنجی/escape می‌شود و از stdin یا فایل موقت با مجوز `0600` به MariaDB می‌رسد، نه از آرگومان خط فرمان.
- `wp-config.php` ناشناس، symlink در هسته، دیتابیس بیگانه یا نشان مالکیت ناسازگار باعث توقف می‌شود و منابع موجود بازنویسی نمی‌شوند.
- فعال‌سازی release اتمی است. اگر Nginx یا Health Check شکست بخورد، release قبلی بازگردانده می‌شود و اگر قبلی وجود نداشته باشد سایت تازه غیرفعال می‌شود.
- مسیرهای سفارشی به‌طور خودکار برای وب باز نمی‌شوند. مسیر را زیر شاخه‌ای قرار بده که `www-data` از قبل بتواند از آن عبور کند یا از مسیر استاندارد `/var/lib/arg/deployments` استفاده کن.

این جریان فقط روی VPS محلی اجرا می‌شود و WordPress را روی Node راه دور پیکربندی نمی‌کند. ارسال ایمیل، بکاپ، افزونه/قالب، رکورد DNS خارجی یا دامنهٔ staging نیز خودکار ساخته نمی‌شوند.
