# معماری پلتفرم اپلیکیشن

این سند baseline فاز ۰۰ و تصمیم‌های معماری لازم برای گسترش ARG از مدیریت میزبان به مدیریت چرخهٔ عمر اپلیکیشن را ثبت می‌کند. این متن وضعیت فعلی مخزن و محدودیت‌هایی را که فازهای بعدی باید حفظ کنند توضیح می‌دهد؛ قابلیت برنامه‌ریزی‌شده به معنی انتشار آن نیست.

## وضعیت فعلی مخزن

ARG یک سرویس مستقل Rust/Axum با رابط React/TypeScript/Vite است. خروجی Frontend داخل باینری Release قرار می‌گیرد. SQLite حساب‌های پنل، نشست‌ها، تنظیمات، Audit، نمونه‌های مانیتورینگ و metadata قابلیت‌ها را نگه می‌دارد. عملیات نیازمند دسترسی بالاتر از مرز Unix socket خصوصی به Helper محدودشده عبور می‌کنند.

ماژول‌های اصلی شامل `src/federation.rs`، `src/nginx.rs`، `src/docker.rs`، `src/s3/`، `src/files.rs`، `src/metrics.rs` و `src/maintenance.rs` هستند. Federation امکان جفت‌کردن ARGها، خواندن وضعیت و سرویس‌های راه‌دور و proxy کردن فضای‌کار احراز‌شده به Node انتخاب‌شده را دارد. سایت‌های Nginx، منابع Docker و Bucketهای S3 همچنان منابع همان سروری هستند که روی آن قرار دارند؛ در baseline فعلی موجودیت یکپارچهٔ Application نداریم. در Routeهای فعلی `/api/apps` یا Job Engine پایدار برای Deploy اپلیکیشن وجود ندارد.

ساخت SQLite و سازگاری مرحله‌ای دیتابیس فعلاً در `src/main.rs` متمرکز است. schemaهای جدید اپلیکیشن باید با migrationهای افزایشی و idempotent اضافه شوند و داده‌های کاربران، نشست‌ها، Nodeها، S3، Nginx و Docker را حفظ کنند. نسخهٔ پروتکل Node فعلی `arg-node/2` است؛ هر تغییر سازگاری پروتکل باید جداگانه بررسی شود.

ARG باید روی یک VPS بدون Node جفت‌شده و بدون Docker همچنان کامل و مفید باشد. وابستگی‌های اختیاری نباید اجباری شوند. نبود Docker، PHP، Node.js، S3 یا قابلیت شبکه باید صادقانه `در دسترس نیست` نشان داده شود، نه وضعیت سالم ساختگی.

## تصمیم معماری: کنترل محلی و سرورهای راه‌دور

### تصمیم

هر نصب ARG کنترل‌سنتر مستقل و کامل میزبان خودش باقی می‌ماند. یک ARG جفت‌شده می‌تواند از طریق درخواست‌های Federation احراز‌شده و دارای scope مشخص مدیریت شود. در شروع، وقتی ARG روی VPS مقصد نصب است، بستهٔ Agent جداگانه لازم نیست.

پنل کنترل مسیر درخواست را فراهم می‌کند؛ سروری که مالک منبع است همچنان منبع حقیقت آن منبع می‌ماند. Controller فقط metadata جفت‌شدن و دادهٔ راه‌دوری را که برای مسیریابی یا خلاصهٔ صریحاً «آخرین وضعیت شناخته‌شده» لازم است نگه می‌دارد. دادهٔ Node نباید بی‌صدا کپی یا cache کهنه به‌عنوان زنده نمایش داده شود.

### هویت و نام‌ها

هر نصب شناسهٔ تغییرناپذیر `server_uuid` دارد. hostname سیستم فقط metadata مشاهده‌شده است؛ هویت شبکه نیست و ARG نباید ضمن یک عملیات دیگر آن را تغییر دهد. `public_name` نام مدیریتی است که به Nodeهای جفت‌شده اعلام می‌شود. `local_label` نام مستعار محلی همان Controller است و به Nodeهای دیگر ارسال نمی‌شود. UI باید دقیقاً بگوید کدام نام تغییر می‌کند و مقصد عملیات را پیش از هر Write نمایش دهد.

Pairingهای قبلی با migration افزایشی و بدون تغییر Node ID یا باطل‌کردن اعتبارنامهٔ سالم حفظ می‌شوند. Handshake پروتکل v2 اکنون UUID پایدار سرور و نام عمومی را به‌صورت اختیاری منتقل می‌کند و یک endpoint احراز‌شده تغییر نام عمومی را با پنل‌های جفت‌شده همگام می‌کند. Nodeهای قدیمی تا زمان اعلام UUID پایدار با کلید فضای‌کار `legacy:<local-id>` کار می‌کنند. برچسب محلی Controller جدا می‌ماند و به Nodeها ارسال نمی‌شود.

### وضعیت پیاده‌سازی فاز ۰۱

- UUID نصب‌های جدید هنگام نیاز در تنظیمات SQLite ذخیره می‌شود؛ فیلدهای هویت به Pairingهای فعلی افزوده می‌شوند و Pairing دوباره ساخته نمی‌شود.
- نام عمومی سرور مستقل از hostname سیستم تنظیم می‌شود. Controller دریافت‌کننده برچسب محلی خودش را جدا نگه می‌دارد.
- حالت تک‌سرور و چندسرور ترجیح رابط هستند و تغییرشان Pairing را حذف نمی‌کند. حالت چندسرور گزینه‌های سرور محلی، نمای خواندنی همهٔ سرورها و فضای‌کار Nodeهای راه‌دور را دارد.
- انتخاب فضای‌کار راه‌دور در `sessionStorage` ذخیره و با UUID پایدار مسیریابی می‌شود. انتخاب عددی قبلی هنگام بارگذاری فهرست Nodeها مهاجرت می‌کند؛ Nodeهای قدیمی کلید legacy مشخص دارند. خروج از حساب فضای‌کار فعال را پاک می‌کند و سوییچ مقصد cache سنگین را پاک می‌کند.
- Routeهای proxy فضای‌کار و ترمینال فقط UUID معتبر یا کلید legacy صریح را می‌پذیرند. Routeهای مدیریت Node همچنان شناسهٔ عددی محلی دارند.
- تغییر نام عمومی با کانال Federation احراز‌شدهٔ HTTPS به سرورهای جفت‌شده ارسال می‌شود؛ قطع ارتباط بخشی به مدیر گزارش می‌شود.
- نمای همهٔ سرورها هر Node راه‌دور را هنگام درخواست بررسی می‌کند، شکست اتصال را «در دسترس نیست» نشان می‌دهد و پیش از مدیریت به انتخاب صریح فضای‌کار نیاز دارد. هنگام شکست هیچ عملیاتی به سرور دیگری منتقل نمی‌شود.
- تست migration و route فاز ۰۱ اضافه شده است. برای اجرای تست Rust، محیطی با Rust toolchain و فرمان `cargo test --locked` لازم است.

### وضعیت پیاده‌سازی فاز ۰۲

- نقش‌ها `standalone`، `member`، `controller-capable` و `both` هستند. تغییر نقش با تأیید انجام می‌شود و اگر باعث یتیم‌شدن Node یا Controller جفت‌شده شود، تعداد وابستگی‌ها گزارش و عملیات متوقف می‌شود.
- کد اتصال یکی از دو سطح فقط‌خواندنی یا کامل را صادر می‌کند. سرور مقصد scope هر Controller را ذخیره و برای هر درخواست بررسی می‌کند؛ Controller نیز پیش از route کردن درخواست مجوز اعطاشده را کنترل می‌کند.
- مقصد روی نشست‌های فضای‌کار راه‌دور guard اعمال می‌کند. خواندن، نوشتن، ترمینال و اجازهٔ ورود به Root Terminal scopeهای جدا دارند. نشست قدیمی به‌جای حفظ دسترسی کامل مدیر، با scope فقط‌خواندنی مهاجرت می‌شود.
- نسخهٔ قابلیت‌ها هنگام جفت‌سازی مذاکره می‌شود. Node قدیمی یا فاقد قابلیت proxy/terminal در وضعیت legacy و فقط‌خواندنی مشخص می‌ماند و عملیات ناسازگار پاسخ `Upgrade Required` می‌گیرد.
- کلید Controller با فایل pending امن و retry idempotent چرخانده می‌شود. نشست فضای‌کار پس از ۱۲ ساعت منقضی و پیش از استفاده تمدید می‌شود. لغو اتصال Controller، نشست‌های راه‌دور همان Controller را هم حذف می‌کند.
- درخواست‌های راه‌دور HTTPS با اعتبارسنجی گواهی، redirect خاموش، timeout محدود، کنترل DNS و pin کردن IP resolve‌شده در درخواست‌های HTTP اجرا می‌شوند. مقصد private به انتخاب صریح نیاز دارد؛ loopback، link-local و آدرس metadata همیشه رد می‌شوند.
- وضعیت‌های `healthy`، `degraded`، `offline`، `untrusted` و `incompatible` به همراه زمان بررسی و خطای پاک‌سازی‌شده ذخیره می‌شوند. Write راه‌دور در مقصد با نام Controller جفت‌شده Audit می‌شود.
- تست‌های Rust شاخهٔ `development` شامل نقش/scope، مجوز نشست، تشخیص آدرس خصوصی، اعتبارسنجی endpoint و migration هستند. برای ادعای پوشش end-to-end هنوز اجرای واقعی بین دو VPS و TLS لازم است.

### واژگان و مالکیت

| اصطلاح | معنی |
| --- | --- |
| سرور | یک نصب ARG و میزبان Linux تحت مدیریت آن؛ شناسهٔ پایدار `server_uuid`. |
| Controller | نصب ARG که به سرور جفت‌شده درخواست احراز‌شده می‌فرستد. |
| سرور مدیریت‌شونده | نصب مقصد که هویت Controller را بررسی و درخواست محدود را محلی اجرا می‌کند. |
| فضای‌کار | context درخواست/رابط: سرور محلی یا یک سرور راه‌دور که صریحاً انتخاب شده است. |
| Application | پروژهٔ قابل استقرار که دقیقاً یک سرور مالک آن است. |
| Service | پردازش یا Container متعلق به اپ؛ مانند web، worker یا database. |
| Environment | محدودهٔ تنظیمات اپ مانند development، staging یا production. |
| Resource adapter | اتصال کنترل‌شده به منبع موجود میزبان، مانند Nginx، Docker، systemd، دیتابیس یا S3. |

یک سایت Nginx یا Container می‌تواند به Application متصل شود، ولی نباید دوباره ساخته یا بی‌اجازه تحت مالکیت ARG قرار گیرد. واردکردن منبع موجود نیازمند پذیرش صریح مالکیت و بررسی تعارض است.

### مسیریابی و مجوز

- هر خواندن یا نوشتن راه‌دور `server_uuid` مقصد مشخص دارد؛ انتخاب فضای‌کار به‌تنهایی مجوز نیست.
- «همهٔ سرورها» نمای تجمیعی/خواندنی است. تغییر از این صفحه باید مقصد مشخص بخواهد.
- Controller کاربر را محلی احراز می‌کند، اما سرور مقصد باید اعتبارنامه، عامل، قابلیت، scope و عملیات را مستقلاً بررسی کند.
- کد مرورگر نباید توکن خام Federation یا اعتبارنامهٔ فضای‌کار راه‌دور را دریافت یا ذخیره کند.
- توکن Controller عمر محدود و rotation دارد، لغو آن فوری است و مقصد Audit را ثبت می‌کند. نشست فضای‌کار پس از ۱۲ ساعت منقضی می‌شود و از کانال احراز‌شدهٔ Controller تمدید می‌شود؛ کلید pending برای retry rotation روی دیسک امن Controller می‌ماند.
- مذاکرهٔ پروتکل قابلیت‌ها و بازهٔ نسخه را اعلام می‌کند. اگر سازگاری امن احراز نشد، عملیات unavailable است؛ نباید بی‌صدا به عملیات گسترده‌تر تنزل کند.
- درخواست راه‌دور محدودیت اندازه و زمان، idempotency برای write قابل‌تکرار و خطای ساختاریافته دارد. Stream باید backpressure و لغو داشته باشد.

### مرز دسترسی ریشه

مرورگر ← API احراز‌شدهٔ Axum ← عملیات دامنه‌ای اعتبارسنجی‌شده ← Helper محدود روی Unix socket، فقط وقتی root لازم است. کد پروژه و فرمان‌های Build ورودی غیرقابل‌اعتمادند؛ باید با کاربر غیرریشهٔ اختصاصی اپ و context محدود اجرا شوند و هرگز به شکل shell string ساخته‌شده توسط کاربر به Helper privileged داده نشوند. Helper نیز عملیات ساختاریافته و allowlist را جداگانه اعتبارسنجی می‌کند.

### مالکیت Application و Job

هویت اپ و وضعیت Deploy را سروری نگه می‌دارد که اپ روی آن اجرا می‌شود. Controller می‌تواند درخواست را route کند، ولی نباید یک نسخهٔ authoritative دوم بسازد. عملیات طولانی Job پایدار با مقصد، عامل، state، Log محدود، رفتار لغو، idempotency و بازیابی پس از restart هستند. UI وضعیت را از Job و مشاهدهٔ واقعی میزبان می‌گیرد، نه از عمر HTTP request.

### ذخیره‌سازی و مهاجرت

- دادهٔ پایدار scope سرور دارد. تغییر فضای‌کار فایل، Volume، دیتابیس یا Secret را جابه‌جا نمی‌کند.
- S3 فضای Object است. Mount لایهٔ سازگاری اختیاری است و تضمین POSIX ندارد؛ فایل دیتابیس و کاری که قفل POSIX لازم دارد نباید روی Mount S3 قرار گیرد.
- انتقال اپ بین سرورها تغییر یک شناسه نیست: preflight، snapshot، انتقال، restore، verify، cutover و پاک‌سازی گام‌های مستقل‌اند.
- تضمین rollback در مرز cutover تعریف می‌شود. پس از پذیرفتن write در مقصد، بازگشت به مبدأ ممکن است writeها را از دست بدهد، مگر reverse sync یا پنجرهٔ maintenance در نظر گرفته شده باشد.
- migrationهای SQLite افزایشی، idempotent، با backup پیش از تغییر پرخطر و آزمون روی دیتابیس تازه و موجود هستند؛ داده‌های نامرتبط ARG را حفظ می‌کنند.

## Gate فازها و ماتریس تست

پیش از اجرای اپلیکیشن باید baseline قابل‌تکرار برای Frontend، Rust، Shell، مستندات و هماهنگی نسخه ثبت شود. وضعیت این محیط در زمان Phase 00: فرمان `cargo` نصب نیست، پس اجرای تست Rust در این Workspace قابل ادعا نیست.

| محیط | پوشش لازم |
| --- | --- |
| یک VPS بدون Docker | سازگاری نصب/ارتقا، مدیریت محلی، عدم وابستگی پنهان به Node راه‌دور. |
| یک VPS با Docker و Runtimeها | مالکیت منابع، وضعیت سرویس، Storage، Log و نبود وابستگی اختیاری. |
| دو VPS جفت‌شده | Pair، سوییچ فضای‌کار، مسیریابی، revoke، همگام‌سازی هویت و Audit دوطرفه. |
| VPS راه‌دور خاموش | برچسب stale، timeout، retry، منع write مبهم و بازیابی پس از اتصال. |
| عملیات قطع‌شده یا کمبود دیسک | بازیابی Job، لغو، مرز rollback و حفظ اطلاعات کاربر. |
| نسخه‌های متفاوت پروتکل | مذاکرهٔ قابلیت، وضعیت unsupported و نبود fallback ناامن. |

هر فاز باید تست همان رفتار را اضافه کند؛ ماتریس نهایی جایگزین تست مرحله‌ای نیست. عملیات حساس به امنیت باید در مرز API هم تست مجوز داشته باشد، نه فقط در UI.

## موجودی Phase 00 مخزن

- **Backend:** Rust/Axum. ثبت Route در `src/routes.rs` است؛ ماژول‌های دامنه شامل Federation، Nginx، Docker، S3، Files، MySQL، Metrics و Maintenance هستند.
- **Frontend:** React، TypeScript، Vite، Tailwind و اجزای Radix/shadcn. ناوبری در `frontend/src/navigation.ts` و Shell در `frontend/src/App.tsx` است.
- **Persistence:** SQLite؛ ساخت schema فعلی در `src/main.rs` متمرکز است. کار جدید نباید وابستگی این فایل بزرگ را بیشتر کند.
- **دسترسی privileged:** سرویس ARG از Unix socket خصوصی با `arg-privileged.service` حرف می‌زند. هیچ قابلیتی نباید آن را به runner عمومی root تبدیل کند.
- **Federation:** پروتکل v2 و proxy فضای‌کار API/Terminal دارد. نقش سرور، scopeهای مقصد، مذاکرهٔ capability نسخهٔ ۱، تمدید نشست، چرخش کلید و وضعیت سلامت در فاز ۰۲ افزوده شده‌اند؛ تست واقعی دو VPS همچنان لازم است.
- **پلتفرم اپ:** در این baseline، Application یکپارچه، runner اپ و Job Engine پایدار Deploy وجود ندارد.
- **CI:** GitHub Actions برای CI و انتشار مستندات وجود دارد. دستورهای تست محلی در `docs/en/development.md` ثبت شده‌اند.
- **نسخه‌بندی:** نسخه‌های Rust و Frontend هماهنگ‌اند؛ ابزارهای پایدار و prerelease به‌ترتیب `scripts/bump-version.sh`، `scripts/bump-development-version.sh` و `scripts/check-versioning.sh` هستند.

## مواردی که پیش از پیاده‌سازی باید دوباره تصمیم‌گیری شوند

۱. Runner اولیه با systemd بومی، Container یا adapter قابل انتخاب ساخته شود؟ سطح ایزوله‌سازی را نباید بیشتر از مرز اجرای واقعی وعده داد.
۲. سایت‌های Nginx و Containerهای موجود چگونه کشف، وارد Application و از مالکیت تکراری محافظت می‌شوند؟
۳. rotation نشست و credential چطور pairing فعلی را بدون قطع دسترسی یا باقی‌ماندن نشست بلندمدت مهاجرت می‌دهد؟
۴. اولین محیط انتشار دقیقاً کدام نسخه‌های Ubuntu/Debian و معماری و حداقل RAM/دیسک را پشتیبانی می‌کند؟ دسترسی بسته‌ها میان نسخه‌ها متفاوت است.
۵. کدام نوع داده با rollback آزمایش‌شده قابل انتقال است و کدام نیاز به downtime یا رفتار best-effort دارد؟
