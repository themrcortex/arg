## شاخه‌ها

- **`main`:** پایدار و پیش‌فرض.
- **`development`:** آزمایشی؛ ممکن است ناپایدار یا دارای تغییرات منتشرنشده باشد. روی VPS حساس، بدون snapshot و مسیر SSH جایگزین نصب نکن.

انتخاب شاخه تعیین می‌کند Update از کدام branch GitHub fetch شود و version/API کدام را build کند.

## روش به‌روزرسانی

- **Release آماده · پیشنهادی و پیش‌فرض:** باینری همان نسخه را از GitHub Releases می‌گیرد؛ SHA-256 و معماری بررسی می‌شوند و نام تگ/فایل با نسخهٔ سورس تطبیق دارد. خود workflow انتشار نیز پیش از ساخت Release، خروجی `--version` باینری را بررسی می‌کند. روی VPS کامپایل انجام نمی‌شود و CPU، RAM و فضای `target` درگیر نمی‌شوند. Release برای Linuxهای `x86_64` و `aarch64` منتشر می‌شود.
- **کامپایل از سورس:** کد شاخهٔ انتخابی را روی VPS می‌سازد. در این روش، Fast یا Complete تعیین می‌کند Cache کامپایل حفظ یا پاک شود.

برای `development` هم دریافت Release فقط وقتی ممکن است که همان نسخهٔ prerelease به GitHub Releases منتشر شده باشد؛ در غیر این صورت روش «کامپایل از سورس» را انتخاب کن. نصب Release بعد از دانلود، checksum و نسخه را کنترل می‌کند و سپس باینری را به‌صورت اتمیک جایگزین می‌کند؛ در شکست، نسخهٔ فعال دست‌نخورده می‌ماند. فایل checksum همراه همان Release منتشر می‌شود و صحت انتقال را کنترل می‌کند؛ امضای مستقل خارج از حساب GitHub پروژه نیست.

## حالت Cache

- **Fast:** `target` و Cache کامپایل Rust را نگه می‌دارد. Updateهای بعدی عموماً سریع‌تر می‌شوند، اما فضای دیسک مصرف می‌ماند.
- **Complete:** پیش از Build Cache قبلی را پاک می‌کند و پس از موفقیت/پایان Build Cache را دوباره پاک می‌کند. در لحظهٔ compile فضای موقت لازم است؛ این روش بدون دیسک موقت build نیست، اما مصرف پایدار Cache را پایین می‌آورد و زمان بیشتری می‌گیرد.

حجم Cache به Rust target، معماری و dependencyها وابسته است؛ مقدار ثابت برای همهٔ سرورها وجود ندارد. حالت complete، source و باینری نصب‌شده یا rollback را پاک نمی‌کند.

### محافظت از منابع هنگام Build

نصب‌کننده قبل از کامپایل فضای آزاد فایل‌سیستم سورس را بررسی می‌کند: برای Build کامل حداقل ۲ GiB و برای حالت سریع حداقل ۱ GiB لازم است. در حالت کامل، ابتدا Cargo target قبلی پاک می‌شود و سپس فضا بررسی می‌شود. اگر فضای کافی نباشد، Build شروع نمی‌شود تا دیسک بی‌دلیل پر نشود.

نصب‌کننده RAM و Swap آزاد، ظرفیت RAM محدودشده با cgroup و تعداد هسته‌های CPU قابل‌استفاده را بررسی می‌کند. در حالت **Fast** پروفایل Rust برای همان VPS ثابت می‌ماند: وابستگی‌ها با opt-level 2 و تعداد codegen unit ثابت براساس ظرفیت RAM و CPU کامپایل می‌شوند؛ فقط تعداد Cargo jobها با RAM آزاد تغییر می‌کند. از ۴ GiB حافظهٔ در دسترس به بالا، تعداد jobها تقریباً یک job به‌ازای هر ۲ GiB است و از تعداد CPUهای قابل‌استفاده بیشتر نمی‌شود. زیر ۴ GiB یک job اجرا می‌شود تا خطای OOM تکرار نشود. خود crate مربوط به ARG در Fast با سطح بهینه‌سازی ۱ ساخته می‌شود. تغییر فشار موقت RAM بنابراین Cache وابستگی‌ها را بی‌دلیل نامعتبر نمی‌کند. حالت **Complete** از پروفایل Release پروژه و محدودیت‌های محافظه‌کارانهٔ حافظه استفاده می‌کند. زیر ۲ GiB نصب‌کننده تلاش می‌کند Swap موقت تا سقف ۲ GiB در `/var/tmp` بسازد؛ پس از Build آن را خاموش و حذف می‌کند. اگر کرنل یا فایل‌سیستم اجازهٔ Swap ندهد، دلیلش را گزارش می‌کند و Build با تعداد job محدود ادامه می‌یابد. باینری فعال پنل فقط پس از موفق‌شدن کامپایل جایگزین می‌شود.

در صورت شکست کامپایل، باینری فعال جایگزین نمی‌شود. نتیجهٔ شکست ثبت، فایل‌های موقت پاک و قفل Update آزاد می‌شود. در حالت Fast، artifactهای وابستگی که با موفقیت کامپایل شده‌اند حفظ می‌شوند تا retry دوباره از صفر شروع نکند؛ فقط حالت Complete target را برای آزادکردن دیسک پاک می‌کند.

## SSH

از گزینهٔ Update در منو شاخه و حالت را انتخاب کن. دستور غیرتعاملی:

```bash
sudo arg update main complete release
sudo arg update development fast source
```

ترتیب ورودی‌ها branch، حالت Cache و روش به‌روزرسانی است. روش `release|source` و حالت Cache `fast|complete` هستند. حالت Cache فقط روی کامپایل از سورس اثر دارد. اگر فقط `sudo arg update` اجرا شود و TTY داشته باشی، شاخه و روش انتخاب می‌شوند؛ Release گزینهٔ پیش‌فرض است.

## بروزرسانی از پنل

دیالوگ Update وضعیت نسخه و commit، شاخه، روش Release یا Source، مرحلهٔ کار و log قابل مشاهده را نشان می‌دهد. Release روش پیشنهادی است و بدون کامپایل محلی نصب می‌شود؛ Fast/Complete فقط پس از انتخاب Source نمایش داده می‌شود. یک Update معتبر در لحظه روی سرور قفل می‌گیرد تا عملیات متناقض از کاربر دیگر هم‌زمان اجرا نشود. دیگر نشست‌ها هم وضعیت جاری را می‌بینند.

در حین Update، سرویس وب ممکن است موقتاً restart شود. پس از دریافت/بررسی Release یا کامپایل Source، نصب باینری، restart و health check انجام می‌شود. Overlay جلوی کلیک عملیات متناقض را می‌گیرد. در پایان UI تلاش می‌کند cache مرورگر را دور بزند و نسخهٔ تازه را reload کند.

## انتشار نسخه

نسخهٔ پایدار `main` با تگ `vX.Y.Z` منتشر می‌شود؛ نسخهٔ آزمایشی `development` با `vX.Y.Z-dev.N`. پس از push شدن تغییر نسخه و commit شاخه، دستور `scripts/publish-release-tag.sh` تگ را می‌سازد و push می‌کند. GitHub Actions برای `x86_64` و `aarch64` باینری musl می‌سازد، `--version` و معماری را بررسی می‌کند، SHA-256 می‌سازد و GitHub Release را منتشر می‌کند. روی `main` فقط نسخهٔ stable تگ می‌شود؛ تگ‌های development به‌صورت prerelease مشخص می‌شوند.

## لغو و Rollback

`cancel-update` یا دکمهٔ لغو درخواست توقف Build/فرایند امن را می‌دهد. لغو ممکن است زمان ببرد تا مرحلهٔ امن برسد. اگر Binary جدید نصب شده و health check شکست بخورد، نصب‌کننده نسخهٔ قبلی و snapshot دیتابیس را بازمی‌گرداند. اگر سرویس قدیمی به‌علت خرابی محیط بالا نیاید، از SSH log و Backup مستقل استفاده کن.

Rollback بازگرداندن دیتابیس هم دارد؛ تغییرات دیتابیس ایجادشده بعد از snapshot قبلی ممکن است از بین برود. پیش از Update مهم، backup مستقل و کنسول VPS داشته باش.

## عیب‌یابی Update

```bash
sudo arg status
sudo arg logs 200
sudo journalctl -u arg -n 200 --no-pager
sudo arg cancel-update
sudo arg rollback
```

اگر قفل stale ماند، ابتدا process و systemd job واقعی را بررسی کن. هرگز فایل `/run/arg-update*` را هنگام Build واقعی دستی پاک نکن. خطای شبکهٔ GitHub، space exhaustion، Rust toolchain یا `cargo` را از همان log تفکیک کن.

## تنظیم شاخه و روش Build

در صفحهٔ بروزرسانی شاخهٔ **main** نسخهٔ پایدارتر را دنبال می‌کند؛ **development** برای آزمایش و تغییرات زودتر است و احتمال regression بیشتری دارد. برای production main را انتخاب کن. شاخهٔ انتخابی منبع نسخهٔ بعدی updater است؛ بعد از تغییر branch، نام/commit دریافتی و release notes را بررسی کن. `development` را فقط وقتی انتخاب کن که اشکال مشخصی را آزمایش می‌کنی و rollback در دسترس است.

حالت **آپدیت سریع** Cache وابستگی‌های Rust را نگه می‌دارد و خود crate برنامهٔ ARG را افزایشی می‌سازد. پروفایل وابستگی‌های Fast روی همان VPS ثابت است؛ تغییر RAM آزاد تعداد jobها را عوض می‌کند اما باعث کامپایل مجدد کل dependencyها نمی‌شود. وقتی حافظه کافی باشد Cargo چند job را موازی اجرا می‌کند و تا هسته‌های مجاز سرور بالا می‌رود؛ روی VPS کم‌حافظه عمداً یک job می‌ماند تا rustc با OOM کشته نشود. نخستین Fast پس از تغییر پروفایل، Cache خالی یا تغییر `Cargo.lock` باید وابستگی‌های تازه را کامپایل کند. خود ARG با سطح بهینه‌سازی ۱ و وابستگی‌ها با سطح ۲ ساخته می‌شوند. **آپدیت کامل** Cache را قبل از Build پاک و پس از پایان دوباره حذف می‌کند؛ زمان بیشتری می‌برد ولی فضای دائمی کمتری می‌گیرد. `target` می‌تواند چندین GiB باشد؛ برای VPS کم‌دیسک Complete و برای آپدیت‌های مکرر Fast را انتخاب کن.

## زمان اجرا، Cancel و Rollback

مرحلهٔ Fetch، کامپایل، نصب helper/فایل‌ها، restart و health-check را از هم تشخیص بده. درصد کامپایل تخمینی است چون `cargo` درصد دقیق قابل‌اعتماد برای تمام مراحل نمی‌دهد؛ متن مرحله و زمان آخرین پیشرفت واقعی‌تر است. بسته‌بودن مودال به معنی stop شدن فرایند نیست.

**Cancel update** فقط درخواست جاری updater را متوقف می‌کند و reservation/lock را آزاد می‌کند. اگر در مرحله‌ای است که binary جابه‌جا می‌شود، منتظر نتیجهٔ rollback/cleanup بمان؛ قفل را با حذف دستی فایل از بین نبر. **Rollback previous version** binary پشتیبانِ ذخیره‌شده را برمی‌گرداند و سرویس را restart می‌کند؛ این کار الزاماً DB migration یا فایل‌های داده را rollback نمی‌کند. قبل از update مهم، از DB/config بکاپ جدا بگیر.

### روال انتشار امن

1. از **Settings/About** نسخه و commit فعلی را یادداشت کن.
2. شاخهٔ درست و روش سریع/کامل را انتخاب کن؛ فضای آزاد دیسک و زمان maintenance را بسنج.
3. اگر پنل در حال کار حساس است Maintenance را فعال کن و backup بساز.
4. Update را اجرا کن و مرحلهٔ Fetch/Build/Install/Health را دنبال کن.
5. فقط پیام موفقیت و health-check را موفقیت تلقی کن؛ پس از نمایش صفحهٔ تازه، cache-busting refresh را اجرا کن.
6. نسخه، ورود، صفحات اصلی و log سرویس را بررسی کن. در شکست، گزارش را ذخیره و در صورت مناسب بودن rollback کن.
