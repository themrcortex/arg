# مدیریت Runtimeها و نسخه‌های زبان

مدیریت Runtime مشخص می‌کند PHP، Node.js، Python و ابزارهای ساخت روی **همین VPS** چه نسخه‌هایی دارند، کدام نسخه‌ها از مخازن APT فعلی قابل نصب‌اند و یک رکورد اپلیکیشن چه نسخه‌ای را نیاز دارد. این بخش نصب حساب یا سرویس خارجی انجام نمی‌دهد.

## از کجا شروع کنم؟

1. به **مدیریت APT** برو.
2. کارت «وضعیت واقعی Runtime و پیش‌بررسی سرور» را بررسی کن. سیستم‌عامل، معماری، Runtimeهای نصب‌شده، ابزارهای مکمل، حافظهٔ آزاد، فضای مسیر استقرار و وجود مخازن APT در آن دیده می‌شود.
3. در «پک زبان‌ها و Runtimeها» نسخه‌ای را که واقعاً از مخازن فعلی سرور آمده انتخاب کن.
4. دکمهٔ پیش‌بررسی را بزن. ARG دستور شبیه‌سازی APT را اجرا می‌کند و فهرست نصب، ارتقا یا حذف احتمالی را نشان می‌دهد.
5. فقط پس از بررسی خروجی، «تأیید و نصب» را انتخاب کن. نصب واقعی از APT پیکربندی‌شده انجام می‌شود.
6. پس از اتمام عملیات، فهرست نسخه‌های نصب‌شده دوباره خوانده می‌شود.

## وضعیت‌هایی که می‌بینی

- **نصب‌شده:** executable سیستم با اجرای نسخهٔ ثابت و بدون shell پیدا شده است.
- **نصب نیست:** inventory نتوانست ابزار را در مسیرهای سیستم بشناسد. این وضعیت به‌تنهایی خطای APT نیست.
- **مخزن پیدا نشد:** فایل منبع APT قابل‌استفاده پیدا نشد؛ فهرست نسخه‌ها ممکن است خالی باشد.
- **توزیع خارج از پشتیبانی:** نصب‌کنندهٔ Runtimeها برای این مسیر فقط Ubuntu و Debian را پیش‌بررسی می‌کند.
- **PHP CLI؛ بدون FPM:** PHP خط فرمان نصب است، اما PHP-FPM همان نسخه پیدا نشده؛ سایت PHP با این مورد به‌تنهایی قابل سرو نیست.
- **FPM غیرفعال:** PHP-FPM نصب است ولی unit آن در لحظهٔ بررسی فعال گزارش نشده است.

مقادیر منابع فقط نمونهٔ لحظهٔ بررسی‌اند؛ حافظه و دیسک قبل از نصب ممکن است تغییر کنند. عدد نامشخص عمداً صفر نمایش داده نمی‌شود.

## پک‌های قابل نصب

ARG فهرست بسته‌ها را از مخازن فعلی APT می‌خواند و برای PHP، Python، Node.js، Java و Ruby نسخه‌های موجود را دسته‌بندی می‌کند. پک PHP اجزای موجود مثل CLI، FPM و افزونه‌های قابل‌دسترسی را کنار هم نشان می‌دهد. پک‌های دیگر نیز فقط شامل نام بسته‌های واقعی همان مخازن‌اند.

ARG به‌صورت پنهان NodeSource یا مخزن شخص ثالث اضافه نمی‌کند و `curl | bash` اجرا نمی‌کند. اگر نسخه‌ای لازم داری که در فهرست نیست، ابتدا منبع رسمی توزیع یا فروشنده را طبق سیاست سرورت تنظیم کن، فهرست APT را به‌روز کن و سپس دوباره نسخه‌ها را بخوان.

پیش‌نمایش، خروجی شبیه‌سازی APT است و تغییرات را اجرا نمی‌کند. بررسی کن که بستهٔ حیاتی حذف نشود یا وابستگی غیرمنتظره وارد فهرست نشده باشد. پس از تأیید، APT ممکن است به‌دلیل مخزن شبکه، قفل بسته یا فضای دیسک شکست بخورد؛ نتیجهٔ واقعی در گزارش عملیات نشان داده می‌شود.

## اتصال نسخه به اپلیکیشن

در فرم ثبت/ویرایش اپلیکیشن، قالب را انتخاب کن تا خانوادهٔ Runtime مربوطه مشخص شود:

- Laravel و WordPress: PHP
- Node.js: نسخهٔ runtime و نسخهٔ جداگانهٔ زمان build
- Python: Python
- سایت استاتیک و قالب سفارشی: Runtime اجباری ندارند

فهرست انتخاب از Runtimeهای نصب‌شدهٔ VPS خوانده می‌شود. برای PHP، فقط نسخه‌ای قابل انتخاب است که PHP-FPM همان نسخه هم نصب باشد. گزینهٔ «نسخهٔ پیش‌فرض سیستم» یعنی اپ نسخهٔ مشخصی را pin نمی‌کند. انتخاب Node برای build از انتخاب Node زمان اجرا جدا ذخیره می‌شود؛ این کار برای پروژه‌هایی که ابزار build و runtime متفاوت دارند لازم است.

این مقدار در رکورد اپلیکیشن به‌عنوان نیازمندی ذخیره می‌شود و با migration افزایشی در دیتابیس قدیمی هم مقدار پیش‌فرض `system` می‌گیرد. در این مرحله ARG هنوز build script را اجرا یا سرویس برنامه را ایجاد نمی‌کند. هنگام اجرای فازهای Runner، همین نیازمندی مبنای preflight و اجرای محدودشده خواهد شد؛ تا آن زمان آن را به‌عنوان «نسخهٔ درخواستی» بخوان، نه اثبات Runtime فعال.

## ابزارهای مکمل

Inventory نسخه و مسیر ابزارهای نصب‌شده را برای موارد زیر بررسی می‌کند: Composer، npm، pnpm، Yarn، Corepack، Nginx و Docker CLI. برای pnpm/Yarn/Corepack کد shim اجرا نمی‌شود؛ نسخه از metadata بستهٔ dpkg خوانده می‌شود تا بازکردن صفحه نتواند مدیر بسته را از اینترنت بگیرد. اگر فایل اجرایی وجود داشته باشد ولی بستهٔ dpkg متناظر پیدا نشود، وضعیت «موجود؛ نسخه تأیید نشد» نمایش داده می‌شود. نبودن هر ابزار مستقل از وضعیت PHP/Node/Python گزارش می‌شود. بازکردن صفحه هیچ‌چیز را نصب نمی‌کند.

## API

- `GET /api/runtimes`: فقط برای مدیر؛ inventory و پیش‌بررسی میزبان را از helper محدودشده می‌خواند.
- `GET /api/packages/runtimes`: پک‌های موجود در مخازن APT فعلی را برمی‌گرداند.
- `POST /api/packages/preview`: فهرست بسته را اعتبارسنجی و نصب را با APT simulation پیش‌نمایش می‌کند.
- `POST /api/packages/action`: عملیات نصب/نگهداری APT؛ ورودی بسته‌ها allowlist و محدودیت تعداد دارد.
- `POST /api/apps` و `PUT /api/apps/{id}`: فیلدهای `runtime_version` و `build_runtime_version` را ثبت می‌کنند. این دو فقط نسخهٔ عددی یا `system` می‌پذیرند.

تمام APIها احراز هویت مدیر دارند. helper تنها نام ابزارها و آرگومان‌های ثابت را اجرا می‌کند؛ متن ورودی کاربر به shell سپرده نمی‌شود.

## عیب‌یابی

### نسخه در پک‌ها نیست

مخازن فعلی آن نسخه را عرضه نمی‌کنند یا فهرست APT قدیمی است. «به‌روزرسانی فهرست» را اجرا و سپس پک‌ها را دوباره بخوان. ARG خودش مخزن بیرونی نصب نمی‌کند.

### PHP دیده می‌شود ولی سایت اجرا نمی‌شود

بررسی کن همان نسخه PHP-FPM نصب باشد، سرویسش فعال باشد و Nginx به socket همان نسخه اشاره کند. PHP CLI به‌تنهایی درخواست وب را پاسخ نمی‌دهد.

### پیش‌نمایش نصب شکست خورد

متن خطا معمولاً به مخزن، نام یا pin نسخه، قفل dpkg یا وابستگی ناسازگار اشاره می‌کند. تا وقتی preview موفق نشده، نصب را تأیید نکن. اگر preview موفق بود ولی نصب شکست خورد، گزارش APT و فضای آزاد دیسک را بررسی کن.

### نسخهٔ اپ در inventory پیدا نشد

آن نسخه را از پک‌های همین VPS نصب کن و فرم اپ را دوباره باز کن. مقدار ذخیره‌شدهٔ قبلی حذف نمی‌شود؛ اگر نسخه هنوز ناشناخته باشد، فرم صریحاً آن را نشان می‌دهد.

## مرزهای فعلی

- نصب Runtime فقط از APT موجود روی Debian/Ubuntu انجام می‌شود؛ ARG مخزن شخص ثالث اضافه نمی‌کند.
- نصب ابزار، پیکربندی Nginx/FPM یا ساخت systemd service برنامه را به‌تنهایی انجام نمی‌دهد.
- انتخاب نسخه، build و اجرای framework را فعال نمی‌کند؛ آن‌ها در فازهای Runner پیاده می‌شوند.
- حذف Runtime وابسته‌ها را حدس نمی‌زند و بخشی از این صفحه نیست؛ حذف بسته می‌تواند به سایت‌های دیگر آسیب بزند و باید در مدیریت APT جداگانه و با پیش‌نمایش انجام شود.
