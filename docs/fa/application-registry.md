# فهرست اپلیکیشن‌ها

صفحهٔ **اپلیکیشن‌ها** فهرست مستقلی از پروژه‌هایی است که روی هر نصب ARG مالکیت آن‌ها ثبت شده است. این فهرست با فایل‌های پیکربندی Nginx و کانتینرهای Docker یکی نیست؛ اتصال یا پذیرش مالکیت آن منابع در گردش‌کار جداگانه انجام می‌شود.

## بازکردن صفحه

از سایدبار، **اپلیکیشن‌ها** را در گروه «اپلیکیشن‌ها و سرویس‌ها» انتخاب کن. این صفحه به دسترسی مدیر نیاز دارد. در فضای‌کار یک VPS، فقط رکوردهای همان VPS خوانده می‌شوند. در حالت **همهٔ سرورها**، فهرست با خواندن Registry محلی و Nodeهای آمادهٔ فضای‌کار جمع می‌شود؛ سرورهای خاموش یا جفت‌نشده با پیام جدا نشان داده می‌شوند. فهرست تجمیعی فقط‌خواندنی است و برای تغییر باید وارد فضای‌کار VPS میزبان شوی.

## ثبت رکورد

روی **ثبت اپلیکیشن** بزن و مشخصات مدیریتی را وارد کن:

| فیلد | کاربرد |
| --- | --- |
| نام | نامی یکتا در همان VPS؛ نام تکراری تا وقتی رکورد فعال است پذیرفته نمی‌شود. |
| قالب پیشنهادی | Laravel، Node.js، Python، WordPress، استاتیک یا سفارشی. این انتخاب فقط metadata است و Runtime نصب نمی‌کند. |
| منبع برنامه | ثبت دستی، مخزن Git، آرشیو، Docker، پوشهٔ موجود یا Image؛ استقرار فعلی Git عمومی، ZIP محدودشده و پوشهٔ مجاز را می‌پذیرد. |
| دامنه | hostname یا IP بدون scheme و port. ARG تعارض را با دامنه‌های ثبت‌شدهٔ دیگر برنامه‌ها و پیکربندی‌های قابل‌خواندن Nginx بررسی می‌کند. |
| پورت TCP | پورت اختیاری میزبان. پورت‌های ثبت‌شدهٔ دیگر و listenerهای فعلی `/proc/net/tcp*` بررسی می‌شوند. این فیلد پورت را bind یا firewall را تغییر نمی‌دهد. |
| وضعیت هدف | خواستهٔ مدیر (`اجرا`، `توقف` یا `تعیین‌نشده`) است؛ تا وقتی observer واقعی وصل نشده، وضعیت مشاهده‌شده همچنان «هنوز مشاهده نشده» می‌ماند. |
| برچسب‌ها و توضیحات | برای جست‌وجو و یادداشت‌های داخلی؛ حداکثر ۲۰ برچسب و ۱۰۰۰ نویسه توضیح. |

پس از ثبت، ARG شناسهٔ UUID و شمارهٔ نسخه برای رکورد ایجاد می‌کند. رکورد روی دیتابیس همان سرور ذخیره می‌شود و نسخهٔ مرجع از Node دیگری کپی نمی‌شود. فیلدهای Secret/Environment در Registry ذخیره نمی‌شوند.

## جست‌وجو و فیلتر

نوار جست‌وجو نام، دامنه، توضیح و برچسب را فیلتر می‌کند. فیلتر چارچوب برای محدودکردن قالب‌هاست. گزینهٔ **نمایش آرشیوی‌ها** رکوردهای حذف نرم‌شده را می‌آورد. اگر یک VPS در نمای تجمیعی پاسخ ندهد، کارت خطا همراه با زمان‌بر نبودن/دلیل دسترسی نشان داده می‌شود و دکمهٔ رفتن به فضای‌کار برای همان VPS در دسترس است.

## ویرایش، آرشیو و بازیابی

ویرایش یک snapshot نسخه‌دار را می‌فرستد. اگر هم‌زمان مدیر دیگری رکورد را تغییر دهد، درخواست با تعارض نسخه رد می‌شود؛ صفحه را تازه کن و تغییر را دوباره وارد کن. **آرشیو** فقط رکورد ARG را از فهرست فعال خارج می‌کند؛ Nginx، فایل‌ها، Container، Volume و سرویس سیستم حذف یا متوقف نمی‌شوند. بازیابی نیز رکورد را برمی‌گرداند و دوباره تعارض نام، دامنه و پورت را بررسی می‌کند.

## تفسیر وضعیت‌ها

- **ثبت‌شده:** شیء مدیریتی در دیتابیس ARG وجود دارد.
- **وضعیت هدف:** خواستهٔ ثبت‌شدهٔ مدیر است، نه گزارش systemd یا Docker.
- **وضعیت واقعی: هنوز مشاهده نشده:** هنوز adapter قابل اتکایی برای مشاهدهٔ اجرای این برنامه وجود ندارد؛ ARG عدد CPU/RAM یا Running ساختگی نشان نمی‌دهد.
- **منابع زنده هنوز متصل نیستند:** هیچ فرایند یا کانتینری به رکورد مالکیت این اپ متصل نشده است.

## وضعیت استقرار

Jobهای پایدار دریافت منبع از کارت محلی اپلیکیشن در دسترس‌اند. وضعیت و تاریخچهٔ مرحله، مدیر، کلید idempotency و سرور مقصد ذخیره می‌شوند؛ لغو، retry، SSE و Rollback release پشتیبانی می‌شود. فایل‌ها در release جدا قرار می‌گیرند و اشاره‌گر `current` اتمی جابه‌جا می‌شود. جزئیات محدودیت‌ها در [استقرار منبع و Jobهای پایدار](./deployment-jobs.md) آمده است. رکورد اپلیکیشن می‌تواند نسخهٔ درخواستی PHP/Node/Python و نسخهٔ جداگانهٔ Node زمان build را از inventory نصب‌شده ذخیره کند؛ راهنما در [مدیریت Runtimeها](./runtime-manager.md) است. این انتخاب هنوز build framework یا فرایند برنامه را اجرا نمی‌کند. Secretهای محیط، HTTP health check، فعال‌سازی Nginx، کنترل منابع، Storage plan و reconciliation غیرفعال‌اند؛ Registry ادعای روشن‌بودن سایت نمی‌کند.

## API و داده

- `GET /api/apps?include_deleted=true` فهرست Registry را برمی‌گرداند.
- `POST /api/apps` رکورد می‌سازد.
- `GET /api/apps/{id}` جزئیات را می‌خواند.
- `PUT /api/apps/{id}` با `expected_version` ویرایش خوش‌بینانه انجام می‌دهد.
- `DELETE /api/apps/{id}` آرشیو نرم می‌کند؛ `POST /api/apps/{id}/restore` بازیابی می‌کند.
- `POST /api/apps/{id}/deploy` برای Git/پوشه Job می‌سازد؛ `/deploy/archive` ZIP محدود می‌پذیرد.
- `GET /api/apps/{id}/deploy/jobs` تاریخچهٔ پایدار را می‌خواند.
- `GET /api/runtimes` inventory مدیرمحور Runtimeها و ابزارهای نصب‌شده را برمی‌گرداند.

جدول‌های `applications` و `application_services` با migration افزایشی و idempotent ایجاد می‌شوند؛ ستون‌های `runtime_version` و `build_runtime_version` نیز به دیتابیس قدیمی اضافه می‌شوند و پیش‌فرض هر دو `system` است. رکوردها `owner_server_uuid` دارند؛ `observed_state` پیش‌فرض `unknown`، `reconcile_policy` برابر `manual`، و بازبینی هم‌زمانی بر پایهٔ `version` است.
