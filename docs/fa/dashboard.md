# داشبورد؛ راهنمای کامل نمای کلی سرور

این صفحه تصویر فشرده‌ای از وضعیت همین لحظهٔ VPS و روند ثبت‌شدهٔ منابع را نشان می‌دهد. داشبورد ابزار اجرای هر نوع فرمان دلخواه نیست؛ برای هر عملیات فقط کنترل‌های صریح ARG را به‌کار ببر. اعداد زنده از API محلی ARG خوانده می‌شوند و نمونه‌های تاریخی از سرویس Rust و پایگاه SQLite می‌آیند. اگر داده‌ای در دسترس نباشد، `—` یا پیام خطا نمایش داده می‌شود؛ صفر فرضی تولید نمی‌شود.

## ورود و اجزای صفحه

از نوار کناری **نمای کلی** را باز کن. بالای صفحه نام میزبان، دکمهٔ **تازه‌سازی** و بنر خوش‌آمدگویی قرار دارند. نام میزبان را می‌توان برای تطبیق با VPS انتخاب‌شده به کار برد؛ این نام لزوماً دامنهٔ وب‌سایت یا IP عمومی نیست. اگر صفحهٔ اشتباه سرور باز شده، نام میزبان را با اطلاعات ارائه‌دهنده یا صفحهٔ **سیستم و منابع** تطبیق بده.

دکمهٔ تازه‌سازی دادهٔ فعلی داشبورد و تاریخچهٔ بازهٔ انتخابی را دوباره می‌خواند. خواندن وضعیت و خواندن تاریخچه دو درخواست جدا هستند؛ ممکن است یکی موفق و دیگری ناموفق شود. در این حالت کارت‌های موفق باقی می‌مانند و هشدار بالای نمودارها می‌گوید کدام بخش دوباره تلاش شود. صفحه به‌طور خودکار هر 15 ثانیه وضعیت و نمونه‌های تاریخچه را تازه می‌کند. وضعیت فایروال، شمار قانون‌های مدیریت‌شده و خلاصهٔ S3 جداگانه هر 30 ثانیه خوانده می‌شوند؛ خطای آن‌ها بقیهٔ داشبورد را از کار نمی‌اندازد.

## کارت‌های شاخص

| کارت | معنی مقدار | چه چیزی را نتیجه نگیریم |
|---|---|---|
| پردازنده | آخرین نمونهٔ CPU ذخیره‌شده به درصد؛ در نبود نمونه `—` | بار یک هستهٔ خاص یا مصرف یک وب‌سایت نیست |
| حافظهٔ RAM | `(کل RAM - حافظهٔ در دسترس) / کل RAM`؛ مقدار کنارش مصرف‌شده و کل را نشان می‌دهد | ممکن است cache سیستم‌عامل در تعریف مصرف اثر بگذارد؛ برای عیب‌یابی OOM لاگ کرنل را هم ببین |
| فضای ذخیره‌سازی VPS | Inventory فایل‌سیستم‌ها؛ خلاصهٔ قابل‌اعتماد فقط در صورت امکان جمع‌زدن Mountهای مستقل | Mountهای تکراری، overlay و pseudo-filesystem نباید چند بار جمع شوند؛ جزئیات را در سیستم و منابع بررسی کن |
| فضای ابری S3 | اتصال‌های سالم، مصرف اندازه‌گیری‌شده و سقف شناخته‌شده، اگر API یا قرارداد آن را بدهد | Bucket بدون Quota را به شکل درصد ساختگی تفسیر نکن؛ مصرف ممکن است اسکن قدیمی باشد |
| زمان روشن‌بودن | ثانیه‌های سپری‌شده از آخرین Boot؛ اگر کمتر از روز باشد به شکل ساعت/دقیقه هم دیده می‌شود | این شاخص uptime خود سرویس ARG نیست |
| میانگین بار | سه مقدار Linux Load Average برای 1، 5 و 15 دقیقه؛ UI مقدار اول را برجسته می‌کند | Load درصد CPU نیست و کارهای منتظر I/O را هم دربرمی‌گیرد |
| مصرف پنل ARG | CPU و RSS فرایند سرویس ARG که سیستم‌عامل گزارش کرده | مصرف همهٔ سایت‌ها، Docker یا دیتابیس نیست |

**نمونهٔ خواندن RAM:** اگر کارت `3.2 GiB از 8 GiB` و `40%` نشان دهد، مقدار اول حافظهٔ مصرف‌شده و مقدار دوم نسبت محاسباتی است. اگر RAM به 95% رسید اما سرور OOM ندارد، قبل از افزایش منابع `free -h`, فرایندهای پرمصرف و `journalctl -k` را هم بررسی کن.

## نمودارها، بازه و زمان

سه نمودار داشبورد CPU، RAM و نرخ شبکه را نمایش می‌دهند. واحد CPU و RAM درصد است. شبکه **نرخ لحظه‌ای نمونه‌ها** را با بایت بر ثانیه برای دریافت و ارسال نشان می‌دهد؛ این نمودار به‌تنهایی حجم تجمعی ماهانه یا ترافیک یک سایت را مشخص نمی‌کند. برای تفکیک رابط و بازه‌های ترافیک به صفحهٔ **شبکه** برو.

فیلترهای آماده عبارت‌اند از **5 دقیقه، 1 ساعت، 24 ساعت، 7 روز و 30 روز**. انتخاب یک فیلتر درخواست تاریخچه را با همان بازه دوباره می‌خواند و نمونه‌ها را از نو تولید نمی‌کند. برای بازهٔ دلخواه، **دلخواه** را انتخاب کن، تاریخ و ساعت شروع و پایان را وارد کن و **اعمال بازه** را بزن. شروع باید پیش از پایان باشد، پایان نباید در آینده باشد و طول بازه حداکثر 366 روز است. نمونهٔ عملی: برای بررسی جهش CPU امروز ساعت 10:00 تا 10:30، هر دو زمان را با منطقهٔ زمانی مرورگر/پنل وارد کن؛ نمودار فقط نقاطی را نشان می‌دهد که قبلاً ذخیره شده‌اند.

نقطهٔ نمودار به زمان ثبت‌شدهٔ خودش تعلق دارد. در بازه‌های چندروزه برچسب محور ممکن است تاریخ و ساعت را ترکیب کند؛ روی نقطه/نشانگر نمودار برو تا زمان دقیق را ببینی. اگر تاریخچه تازه فعال شده، سرور خاموش بوده یا بازه از مدت نگهداری نمونه‌ها قدیمی‌تر است، دادهٔ گذشته قابل بازسازی نیست. **تازه‌سازی** باعث نمونه‌سازی تاریخیِ گذشته نمی‌شود.

### ثبت و نگهداری تاریخچه

نمونه‌گیری در پس‌زمینهٔ ARG انجام می‌شود؛ لازم نیست کاربر داشبورد را باز نگه دارد. تنظیم فعال‌بودن، فاصلهٔ نمونه‌گیری و مدت نگهداری در تنظیمات پایش قرار دارد. خاموش‌کردن تاریخچه ذخیرهٔ آینده را متوقف می‌کند، ولی لزوماً داده‌های قبلی را فوراً پاک نمی‌کند. فاصلهٔ کوتاه‌تر نمودار دقیق‌تری می‌دهد اما تعداد ردیف SQLite، نوشتن روی دیسک و هزینهٔ محاسبات را بالا می‌برد. نگهداری طولانی‌تر فضای بیشتری می‌گیرد. برای VPS کم‌منبع، ابتدا مقدار پیش‌فرض را نگه دار؛ فقط اگر برای تحلیل حادثه به دقت بیشتری نیاز داری interval را کم کن و بعد اندازهٔ DB را بررسی کن.

اگر نوار **تاریخچه متوقف است** دیده می‌شود، تنظیم History را بررسی کن. اگر نمونه‌ای در بازه نیست، بازه را کوتاه‌تر کن یا وضعیت ثبت را کنترل کن؛ 0% معنی «نمونه موجود نیست» ندارد.

## خلاصه‌های شبکه و امنیت

### رابط‌های شبکه

کارت رابط‌ها حداکثر 4 مورد اول API را نشان می‌دهد: نام Interface، اولین نشانی گزارش‌شده و وضعیت لینک. `up` به معنی بالا بودن Interface است، نه تضمین دسترسی از اینترنت. اگر IP مورد انتظار در جدول نیست، **مشاهدهٔ همه** را بزن و صفحهٔ شبکه را برای کارت‌های فعال و جزئیات بیشتر باز کن. نشانی‌های خصوصی مثل `10.x`, `172.16–31.x` و `192.168.x` به‌تنهایی IP عمومی نیستند.

### پورت‌های شنونده

حداکثر 4 Listener اول با شمارهٔ پورت، پروتکل و IPv4/IPv6 نمایش داده می‌شوند. Listener یعنی برنامه روی سرور به آن پورت bind شده است؛ بازبودن مسیر از اینترنت به DNS، فایروال VPS، فایروال ارائه‌دهنده و مسیریابی هم وابسته است. اگر پنل در این فهرست است ولی از بیرون باز نمی‌شود، صفحهٔ **پورت‌ها** و سپس Security Group ارائه‌دهنده را بررسی کن. از داشبورد نمی‌توان نتیجه گرفت که همهٔ پورت‌های نمایش‌داده‌نشده بسته هستند.

### وضعیت UFW

بخش فایروال نشان می‌دهد UFW موجود است یا نصب نیست، فعال است یا غیرفعال، و تعداد قوانین ARG-managed را گزارش می‌کند. این تعداد به معنی شمار همهٔ Ruleهای دستی سیستم نیست. **جزئیات** را بزن تا صفحهٔ UFW را باز کنی. قبل از فعال‌سازی UFW پورت SSH فعلی و پورت پنل را مجاز کن تا اتصال راه دور قطع نشود.

### خلاصهٔ S3

خلاصه از API فضای S3 خوانده می‌شود و خطای آن داشبورد را مختل نمی‌کند. ظرفیت فقط وقتی نشان داده می‌شود که اندازه‌گیری معتبر یا Quota ثبت‌شده موجود باشد. اسکن مصرف S3 معمولاً فهرست Objectها را صفحه‌به‌صفحه می‌خواند؛ عدد stale را با مصرف امروز اشتباه نگیر. برای جزئیات provider و زمان اسکن، وارد **فضای ابری S3** شو.

## Fast Actions: تعریف، اجرا و بررسی نتیجه

Fast Actions پایین بنر و برای مدیر نمایش داده می‌شود. از دکمهٔ **افزودن اکشن** یک اکشن ذخیره‌شده بساز؛ هر کارت فقط عملیات انتخاب‌شده را انجام می‌دهد. گزینه‌ها:

| عملیات | هدف و مثال استفاده | محدودیت |
|---|---|---|
| بررسی کانفیگ Nginx | قبل از Reload، صحت Syntax را کنترل کن؛ مثلاً یک اکشن «بررسی قبل از انتشار» | پیکربندی را تغییر نمی‌دهد |
| Reload Nginx | تنظیمات خوانده‌شده را با کمترین وقفه دوباره بارگذاری کن | خطای Syntax باید اول رفع شود؛ نتیجه را در مودال ببین |
| Restart Nginx | فرایند سرویس را دوباره راه‌اندازی کن | اتصال وب ممکن است موقتاً قطع شود |
| شروع سرویس systemd | یک unit مجاز را Start کن؛ مثلاً worker متعلق به پروژه | از منوی انتخاب سرویس استفاده کن؛ نام دلخواه به‌عنوان دستور پذیرفته نیست |
| Reload سرویس systemd | پیکربندی unit یا سرویس دارای Reload را دوباره بخوان | همهٔ unitها این عملیات را پشتیبانی نمی‌کنند |
| Restart سرویس systemd | سرویس انتخابی را Restart کن؛ نمونه: سرویس worker مستقل پروژه | سایت‌ها و وابستگی‌های متصل را قبلش بررسی کن |
| اکشن سفارشی | اسکریپت کوتاه از پیش تعیین‌شده‌ای را با کاربر سرویس ARG اجرا کن؛ نمونهٔ کم‌خطر: `php artisan queue:restart` در پروژه‌ای که PHP و Artisan دارد | Root نیست، تا 30 ثانیه محدود است، فرمان مستقیم shell دلخواه و privilege escalation ارائه نمی‌کند |

در ساخت/ویرایش، **عنوان دکمه** حداکثر 48 نویسه است؛ **عملیات** نوع کار را تعیین می‌کند. عملیات سرویس یک **واحد systemd** از فهرست وضعیت‌دار می‌خواهد. عملیات سفارشی متن دستور/اسکریپت را تا 2048 بایت می‌پذیرد؛ مسیر و فرمان باید برای کاربر ARG قابل دسترسی باشد. برای نمونه، `php artisan queue:restart` فقط وقتی درست است که working directory/محیط آن پروژه از همان context در دسترس باشد؛ فرمانی بنویس که مستقل و کوتاه اجرا شود و اطلاعات محرمانه در آن نباشد.

دو گزینهٔ گزارش را از هم جدا کن:

- **نمایش لاگ‌های اجرا** خروجی `stdout` و `stderr` همان اکشن سفارشی را در نتیجه می‌آورد؛ هر جریان حداکثر 64 KiB نمایش دارد. این گزینه log فایل پروژه را نمی‌خواند.
- **نمایش Error Log سایت** لاگ خطای Nginx سایت انتخاب‌شده را پس از عملیات ضمیمه می‌کند. سایت را از منوی سایت انتخاب کن؛ اگر مسیر/اجازهٔ خواندن در دسترس نباشد، گزارش خودش خطا می‌گیرد.

برای ساختن نمونهٔ «سلامت Nginx»: عنوان را `بررسی Nginx` بگذار، عملیات **بررسی کانفیگ Nginx** را انتخاب کن، اگر لازم است سایت را برای Error Log انتخاب و Toggle آن را فعال کن، سپس ذخیره کن. برای اجرا روی دکمهٔ Play بزن. مودال ابتدا وضعیت فعلی سرور/Nginx یا سرویس را می‌خواند، مرحلهٔ اجرا را نشان می‌دهد، عملیات را انجام می‌دهد، وضعیت پس از اجرا را دوباره می‌گیرد و نتیجه/خطا/لاگ انتخاب‌شده را نمایش می‌دهد. مودال را تا پایان نبند؛ عملیات تکراری ممکن است اثر جانبی داشته باشد. اگر خروجی وضعیت جدید را تأیید نمی‌کند، به صفحهٔ همان سرویس برو و جزئیات را بررسی کن.

با **ویرایش** عنوان، نوع و هدف را تغییر بده؛ با **حذف** اکشن فقط تعریف ذخیره‌شده حذف می‌شود و سرویس یا فایل پروژه را پاک نمی‌کند. اجرای اکشن سفارشی درخواست تأیید جدا دارد. چون آن فرمان با مجوز حساب سرویس اجرا می‌شود، فقط فرمان‌های کوتاه و ممیزی‌پذیر ذخیره کن، از redirect گسترده، `sudo`, حذف recursive، دانلود و اجرای اسکریپت راه‌دور و رمز داخل command خودداری کن.

## خطاهای رایج و مسیر عیب‌یابی

1. **وضعیت فعلی نمی‌آید:** دکمهٔ تلاش دوباره را بزن؛ اگر فقط نمودار خطا دارد، سرویس history و اتصال SQLite را بررسی کن.
2. **نمودار خالی است:** بازه را کوتاه کن، History را فعال کن و زمان آخرین نمونه را بررسی کن. دادهٔ پیش از فعال‌شدن قابل تولید نیست.
3. **Load زیاد است ولی CPU پایین است:** ممکن است I/O wait عامل باشد؛ صفحهٔ سیستم و نمودار Disk Read/Write را ببین.
4. **Listener دیده می‌شود اما پنل باز نمی‌شود:** Listener فقط وضعیت bind را می‌سنجد؛ UFW، فایروال Provider، TLS و IP را جداگانه بررسی کن.
5. **Fast Action شکست خورد:** متن مرحله/Exit code را بخوان. برای Nginx ابتدا `nginx -t` از پنل یا بررسی کانفیگ را اجرا کن. برای systemd، State واحد را در سرویس‌های سیستم ببین. برای اکشن سفارشی، فرمان را با کاربر `arg` و همان working directory آزمایش کن.
6. **عدد حافظه یا دیسک با ابزار دیگری فرق دارد:** روش شمارش را مقایسه کن. دیسک داشبورد Inventory فایل‌سیستم است؛ Docker overlay، Mount ابری و فایل‌سیستم‌های مجازی ممکن است در جمع فیزیکی وارد نشوند.

## نمونهٔ روال بررسی کندی سایت

1. بازهٔ نمودار را از 5 دقیقه به 1 ساعت تغییر بده تا ببینی کندی لحظه‌ای است یا ادامه‌دار.
2. CPU و RAM را کنار Load بخوان؛ Load بالا به‌تنهایی تشخیص CPU bottleneck نیست.
3. در صفحهٔ شبکه نرخ RX/TX و در سیستم، دیسک و I/O را بررسی کن.
4. Listenerهای 80/443 و فایروال را کنترل کن.
5. در Nginx ابتدا کانفیگ را Test کن، سپس لاگ همان سایت را ببین.
6. اگر Fast Action لازم است، اکشنی محدود و مشخص بساز و نتیجهٔ قبل/بعد را نگه دار. تغییرات پرخطر را از روی یک نمودار تنها اعمال نکن.
