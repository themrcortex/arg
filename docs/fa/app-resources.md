# شبکه، دادهٔ پایدار، S3 و لاگ اپلیکیشن

این صفحه مرز واقعی کنترل‌های منابع اپ را توضیح می‌دهد. مسیر فعلی در کارت اپلیکیشن‌ها، بخش «فضای پایدار، شبکه و S3» است. APIهای این قابلیت فقط برای مدیر در دسترس‌اند و تغییرات مهم در Audit ثبت می‌شوند.

## شبکهٔ اپلیکیشن

### Docker private bridge

از کارت اپ، نامی مثل `backend-private` بده و نوع «Docker private bridge» را انتخاب کن. ARG شبکه‌ای با نام تولیدشده و برچسب مالکیت خودش می‌سازد و گزینهٔ `--internal` را فعال می‌کند؛ این شبکه route عمومی بیرونی ندارد. برای اتصال کانتینر به اپ، هنگام ساخت کانتینر در صفحهٔ Docker اپلیکیشن دارای منبع Docker را انتخاب کن. این کار برچسب `com.arg.application_id` می‌گذارد. در کارت اپ، alias و کانتینر را وارد و اتصال را ثبت کن. Helper دوباره برچسب شبکه و کانتینر را بررسی می‌کند.

ARG کانتینر دلخواهی را فقط به‌خاطر داشتن نام مشابه قبول نمی‌کند. اگر کانتینر با ARG و شناسهٔ اپ ساخته نشده باشد، باید از همان اپ کانتینر جدید بسازی. پیش از حذف شبکه، همهٔ اعضا را جدا کن؛ شبکهٔ دارای عضو حذف نمی‌شود.

### Loopback برای سرویس Native

برای Node/Next/Nuxt که systemd اجرا می‌کند، «Loopback داخلی» یک alias به `127.0.0.1:<port>` ثبت می‌کند. پورت باید همان پورت خود اپ باشد. این روش service discovery ساده برای یک میزبان است؛ process را در Docker قرار نمی‌دهد، firewall یا namespace نمی‌سازد و بین اپ‌ها جداسازی امنیتی ایجاد نمی‌کند.

## فضای دادهٔ پایدار

یک volume با نامی مثل `uploads` بساز. مسیر پایدار Node داخل سرویس `/shared/data/volumes/uploads` است؛ داده بیرون از پوشهٔ release قرار می‌گیرد و با deploy یا rollback جایگزین نمی‌شود. گروه اختصاصی اپ دسترسی نوشتن می‌دهد و پوشهٔ والد از تغییر مسیر توسط خود اپ محافظت می‌شود.

«اندازه‌گیری» اسکن دستی است و حداکثر ۱۰۰هزار ورودی را بررسی می‌کند؛ اندازه‌های symlink دنبال نمی‌شوند. برای جلوگیری از فشار دیسک اسکن پیاپی لازم نیست. سقف اختیاری فقط یادداشت مدیریتی است؛ ARG quota kernel یا محدودیت write اعمال نمی‌کند.

«جداکردن» فقط رکورد مدیریتی را حذف می‌کند و فایل‌ها را نگه می‌دارد. «حذف داده» تأیید جدا می‌خواهد و پوشه را پاک می‌کند؛ اگر مسیر روی filesystem جدا mount شده باشد Helper آن را رد می‌کند. پیش از پاک‌سازی از فایل‌ها backup بگیر.

## اتصال Bucket S3

در همان کارت، Bucket موجود و prefix مثل `customer-a/assets/` را انتخاب کن و کاربرد را مشخص کن: فایل، پشتیبان، artifact، دارایی یا Mount موجود. `rclone-mount` فقط وقتی پذیرفته می‌شود که Mount فعال واقعی برای Bucket ثبت شده باشد.

Binding فقط ارجاع امن به اتصال موجود است؛ secret به اپ یا API آن منتقل نمی‌شود. سطح Read/Write در ARG metadata است و مجوز S3 را تغییر نمی‌دهد. برای جداسازی واقعی، در پنل ارائه‌دهنده کلیدی بساز که فقط به Bucket/prefix همان اپ دسترسی داشته باشد. اگر پوشهٔ Mount را استفاده می‌کنی، mount option و permissionهای خود آن را هم بررسی کن.

اتصال S3 را حذف نمی‌توان کرد تا Bindingهای اپ جدا شوند. جداکردن Binding، آبجکت یا Bucket را پاک نمی‌کند.

## لاگ‌های سرویس Node

«نمایش لاگ‌های اجرا» آخرین رخدادهای واحد systemd همین اپ را می‌خواند. هر درخواست تا ۵۰۰ خط می‌گیرد و cursor برای دریافت رخدادهای جدید بعدی نگه داشته می‌شود. بسته‌شدن مرورگر یا restart سرویس ARG لاگ journald را حذف نمی‌کند.

Retention از تنظیم کلی journald میزبان پیروی می‌کند، نه تنظیم جدا برای اپ. `journalctl --disk-usage` برای دیدن حجم کل مفید است؛ تغییر vacuum روی همهٔ سرویس‌ها اثر دارد و از این کارت اجرا نمی‌شود. مقدارهای secret را در خروجی برنامه چاپ نکن.

## API و رفتار حذف

- `GET/POST /api/app-networks`: فهرست و ساخت شبکهٔ سرور محلی.
- `GET/POST /api/app-networks/{id}/members`: مشاهده و افزودن عضو.
- `DELETE /api/app-networks/{id}/members/{app_id}`: جداکردن عضو.
- `GET/POST /api/apps/{id}/volumes`: فهرست یا ساخت مسیر دادهٔ پایدار.
- `POST /api/app-volumes/{id}/scan`: اندازه‌گیری محدود.
- `DELETE /api/app-volumes/{id}`: حذف metadata و نگه‌داشتن فایل.
- `POST /api/app-volumes/{id}/purge`: پاک‌سازی فایل با تأیید صریح.
- `GET/POST /api/apps/{id}/s3-bindings` و `DELETE /api/app-s3-bindings/{id}`: مدیریت ارجاع Bucket.
- `GET /api/apps/{id}/node/service/logs?limit=100&after=...`: خواندن صفحه‌ای journald؛ `after` cursor خروجی قبل است.

## محدودیت‌های میزبان

تست خودکار مسیرهای اعتبارسنجی، schema و type-check را می‌سنجد. اتصال واقعی Docker، رفتار گروه لینوکس، permissionهای S3 mount و pagination journald باید روی Debian/Ubuntu آزمایشی هم بررسی شود. ارتباط شبکهٔ بین چند VPS در این بخش پیاده نشده است.
