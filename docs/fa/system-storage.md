## اطلاعات سیستم

صفحهٔ سیستم مشخصات میزبان، uptime، CPU، RAM، Swap و فایل‌سیستم‌ها را در یک محل جمع می‌کند. بخش دیسک‌ها mountهای محلی، مجازی و Remote را تفکیک می‌کند؛ یک mount تکراری نباید به‌عنوان ظرفیت مستقل دوباره جمع شود.

## معنی ظرفیت دیسک

- **Total:** بلوک‌های کل فایل‌سیستم.
- **Used:** بلوک‌های اشغال‌شده.
- **Available:** فضایی که برای کاربر عادی قابل استفاده است؛ ممکن است از Free کمتر باشد چون بخشی برای root رزرو شده.
- **Reserved/unavailable:** اختلاف Total با Used و Available در صورت قابل محاسبه بودن.
- **Mount point:** مسیری که فایل‌سیستم درخت دایرکتوری را به آن متصل می‌کند؛ برای مثال `/`, `/var`, `/mnt/data`.

`/proc`, `/sys`, `tmpfs`, `overlay`، cgroup و pseudo-filesystemها فضای فیزیکی مستقل نیستند و از مجموع دیسک‌های محلی کنار گذاشته می‌شوند. Mountهای FUSE/S3 در بخش Remote/Cloud هستند، نه ظرفیت واقعی دیسک محلی. Cache لوکال Rclone همچنان دیسک محلی را مصرف می‌کند.

## تحلیل فضای اشغال‌شده

ابزار تحلیل دیسک با پیمایش محدود، پوشه‌ها و فایل‌های بزرگ را رتبه‌بندی می‌کند. مقدار پوشه، مجموع زیرشاخه‌هاست؛ بنابراین نباید مقدار والد و فرزند را با هم جمع کرد. گزینهٔ پیمایش mountهای دیگر یا شکستن محدودیت اسکن می‌تواند زمان، I/O و بار CPU را زیاد کند. مسیرهای مجازی، دایرکتوری‌های پویا و فایل‌هایی که حین اسکن تغییر می‌کنند ممکن است اختلاف ایجاد کنند.

برای پیدا کردن مصرف واقعی در SSH می‌توان از این فرمان‌های فقط‌خواندنی استفاده کرد:

```bash
sudo df -hT
sudo du -xhd1 /var /opt /home 2>/dev/null | sort -h
sudo docker system df -v
```

`du -x` از رفتن به فایل‌سیستم mountشدهٔ دیگر جلوگیری می‌کند. پیش از حذف cache، Image، log یا release قدیمی، مطمئن شو سرویس فعالی به آن وابسته نیست.

## نمودار Read/Write

نرخ خواندن/نوشتن زمانی نمایش داده می‌شود که counterهای block device در سیستم موجود باشد. این نرخ ترافیک برنامه‌ها را نشان نمی‌دهد و به‌طور کلی نمی‌تواند I/O یک سایت یا Container را جدا کند. مقادیر میان reboot یا تغییر device قابل مقایسهٔ مستقیم نیستند؛ نمودار نرخ و نمودار capacity دو مفهوم متفاوت‌اند.

## ریسک پاک‌سازی

هرگز برای آزادکردن فضا دستی مسیرهای `/var/lib/docker`, `/var/lib/containerd`, دیتابیس، `/opt/arg` یا دایرکتوری سایت را با `rm -rf` پاک نکن. ابتدا مالک داده و اتصال آن به سرویس را پیدا کن؛ از Docker prune فقط پس از بازبینی موارد حذف‌شونده استفاده کن.

## خواندن صفحهٔ سیستم و Mountها

کارت‌های CPU، RAM و دیسک مقدار آخرین خواندن سرور را نشان می‌دهند. Refresh، نمونهٔ فعلی را دوباره می‌خواند؛ انتخاب بازهٔ تاریخچه نمودارها را تغییر می‌دهد و دادهٔ گمشده را نمی‌سازد. CPU درصد مصرف نمونه‌گیری‌شده است، RAM از کل و available محاسبه می‌شود. Load average صف runnable و I/O را هم منعکس می‌کند و درصد نیست.

### فهرست فایل‌سیستم‌ها

در بخش **دیسک‌ها و Mount Pointها** هر Volume جداگانه مسیر Mount، device, filesystem, kind، total/used/available، درصد و read-only/status را دارد. Local، Cloud، Virtual و All را فیلتر کن. روی ردیف بازشونده جزئیات زمان سنجش و خطا را ببین. `statvfs` ظرفیت Mount را اندازه می‌گیرد؛ برای FUSE/S3 ممکن است ظرفیت کل unknown باشد، چون API شیءگرا فضای خالی POSIX تضمین نمی‌کند. Unknown مساوی صفر نیست.

Summary فقط وقتی چند فایل‌سیستم غیرهم‌پوشان قابل تشخیص باشند آن‌ها را جمع می‌کند. Mount تکراری یا bind mount، tmpfs, overlay, `/proc`, `/sys` و `/dev` نباید به عنوان دیسک مستقل فیزیکی دوباره‌شماری شود. اگر KPI دیسک ریشه با ظرفیت کل فرق دارد، مسیر `/` را با ردیف root مقایسه کن؛ KPI ممکن است فقط root را نشان دهد تا وقتی aggregate قابل‌اعتماد نیست.

### ظرفیت، I/O و روند

نمودار Capacity نسبت مصرف به total همان فایل‌سیستم منتخب را نشان می‌دهد. نمودار Read/Write نرخ بایت خواندن و نوشتن دیسک است و ممکن است برای Mount/driver داده نداشته باشد. دادهٔ موجود با زمان آخرین نمونه تفسیر شود؛ صفر، نبود measurement نیست. بازهٔ چندروزه را با tooltip تاریخ بررسی کن.

### تحلیل فضای اشغال‌شده

برای یافتن علت پرشدن VPS، تحلیل Disk را از `/` شروع و زیرشاخه‌های بزرگ را expand کن. اندازهٔ والد شامل فرزندان است و نباید با اندازهٔ زیرپوشه جمع شود. `du` روی دیسک شلوغ I/O می‌زند؛ اسکن مجدد پیاپی CPU/Disk را درگیر می‌کند. برای `/var/lib/containerd` از صفحه Docker و دستور read-only `docker system df -v` استفاده کن. پاک‌سازی imageهای dangling را با حذف volume یا image موردنیاز یکی ندان؛ volume دیتابیس می‌تواند دادهٔ یگانه داشته باشد. Cache، releaseهای قدیمی و build artifacts را فقط وقتی پاک کن که متعلق‌بودن، امکان rebuild و rollback را بررسی کرده‌ای.

**نمونه:** اگر `/opt/arg/source/target` بزرگ است، احتمالاً Rust build output است. Build سریع ممکن است آن را برای آپدیت‌های بعدی نگه دارد؛ حالت کامل فضای کمتری می‌گیرد اما compile زمان‌بر است. حذف `target` برنامهٔ نصب‌شده را مستقیماً پاک نمی‌کند، ولی آپدیت بعدی را مجبور به build کامل می‌کند.

### چه زمانی پاک‌سازی امن است؟

ابتدا فرق فایل فعال، cache قابل بازسازی، backup لازم و artifact قابل rebuild را بفهم. فضای آزاد را در کارت Storage و آخرین سنجش بررسی کن؛ اگر Root روی 95% است، Build/update را هم‌زمان آغاز نکن. برای cleanup این ترتیب کم‌خطرتر است:

1. `/var/cache/apt` را با APT clean پاک کن؛ این آرشیو package دانلودی است.
2. journald را با تنظیم Vacuum/retention مدیریت کن و حجمش را قبل/بعد ببین؛ log امنیتی موردنیاز را حذف نکن.
3. با `docker system df -v` بررسی کن چه مقدار build cache و image واقعاً بلااستفاده است؛ از پنل Docker prune کنترل‌شده انجام بده و volume را نگه دار.
4. release قدیمی برنامه را فقط پس از اطمینان از نسخهٔ جاری و rollback پاک کن.
5. برای هر مسیر بزرگ یک owner بگذار؛ `/home/deploy/apps/site1` ممکن است releaseها، دیتابیس یا فایل upload واقعی داشته باشد.

`du` اندازهٔ directory entryها را می‌خواند و ممکن است hard link، sparse file، deleted-but-open file یا Mountهای جدا را مثل `df` گزارش نکند. اگر `df -h` فضای پر نشان می‌دهد ولی `du` جمعش نمی‌کند، فایل حذف‌شده‌ای که پردازش هنوز باز نگه داشته یا inode تمام‌شده را بررسی کن. فایل پاک‌شدهٔ باز با پاک‌کردن مجدد درست نمی‌شود؛ سرویس نگه‌دارنده را شناسایی و زمان restart ایمن برنامه‌ریزی کن.

### نمونهٔ تفسیر ریشه و Mountها

فرض کن `/` روی 90% است و `/mnt/archive` روی S3 Mount با quota unknown دیده می‌شود. نوار `/mnt/archive` را در جمع فیزیکی `/` وارد نکن؛ cache محلی Rclone که مثلاً زیر `/var/cache/arg-s3` است بخشی از root است. انتقال فایل به S3، فضای root را فقط در صورتی آزاد می‌کند که پس از تأیید copy، فایل محلی را خودت حذف کنی. انتقال امن معمولاً دو مرحله است: copy → checksum/size verify → استفادهٔ برنامه از مقصد جدید → دورهٔ مشاهده → حذف کنترل‌شدهٔ نسخهٔ محلی.

### I/O و Load

اگر CPU پایین اما درخواست‌ها کندند، نمودار Read/Write و مسیرهای `/var/lib/mysql`, `/var/lib/docker` یا logهای پرتکرار را بررسی کن. Read/Write یک snapshot rate است؛ حجم جمعی در بازه از تاریخچه می‌آید. اگر اعداد null هستند، ممکن است کرنل/driver counter ندهد. تغییر storage backend بدون downtime، backup و کنترل mount dependency انجام نده.
