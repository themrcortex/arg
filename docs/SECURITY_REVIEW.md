# گزارش بررسی امنیتی ARG

**مخزن:** `themrcortex/arg`  
**مبنای بررسی اولیه:** نسخه `v0.4.31`، کامیت `1b252f7` (۲۴ اکتبر ۲۰۲۶)

**بازبینی کد:** نسخهٔ کاری `v0.4.33` (۲۵ اکتبر ۲۰۲۶)

**روش:** بررسی ایستا و تست واحد محلی؛ بدون دسترسی به VPS واقعی یا تست نفوذ.
**وضعیت:** موارد ۱ تا ۵ در کد اصلاح یا محدود شده‌اند؛ آزمون عملی روی VPS هنوز انجام نشده است.

## پیگیری اصلاح‌ها در v0.4.33

- هنگام فعال بودن TLS، Listener مربوط به HTTP روی loopback می‌ماند و `install.sh` دیگر پورت backend پنل را در UFW باز نمی‌کند؛ فقط HTTP challenge و پورت HTTPS باز می‌مانند.
- قانون‌های فایروال پورت‌های پیش‌فرض و bindهای فعال ARG و پورت‌های مؤثر SSH از `sshd -T` را محافظت می‌کنند.
- Root Terminal گذرواژهٔ مدیر را دوباره می‌خواهد و یک مجوز کوتاه‌عمر، یک‌بارمصرف و وابسته به نشست جاری می‌سازد.
- عملیات توقف، راه‌اندازی مجدد، غیرفعال‌سازی و mask سرویس ARG، SSH و شبکهٔ اصلی از پنل رد می‌شوند.
- timeout محلی ۱۰ دقیقه‌ای مرورگر در نسخهٔ 0.4.32 حذف شده بود؛ رابط اکنون وضعیت ثبت‌شدهٔ Helper را معیار می‌گیرد. مدت اجرای واقعی Update روی VPS در این بازبینی آزمایش نشده است.
- CI برای Rust و React اضافه شده است. فایل‌های بزرگ `src/main.rs` و `frontend/src/pages.tsx` هنوز نیازمند تفکیک تدریجی‌اند. `frontend/dist` نیز عمداً برای Embed شدن UI در باینری نگهداری می‌شود و باید همراه سورس build شود.

## ۱. بحرانی — در دسترس‌بودن HTTP عمومی پس از فعال‌سازی HTTPS (محدودشده در 0.4.32 و 0.4.33)

- **شواهد:** در `install.sh` مقدار پیش‌فرض `ARG_BIND=0.0.0.0:8282` است. تابع `sync_ufw_rules` در صورت فعال‌بودن UFW این پورت را باز می‌کند. در `src/main.rs` هنگام راه‌اندازی TLS، سرویس HTTP نیز باقی می‌ماند و API ورود بر بستر HTTP قابل استفاده است.
- **پیامد:** ورود مدیر از آدرس HTTP عمومی ممکن است نام کاربری، گذرواژه و نشست را بدون رمزنگاری انتقال دهد.
- **تغییر کد در 0.4.32:** ورود از اتصال غیر loopback بدون `x-forwarded-proto: https` رد می‌شود؛ وقتی TLS برای ARG پیکربندی شده، listener HTTP فقط روی loopback باز می‌شود و کوکی نشست HTTPS ویژگی `Secure` می‌گیرد.
- **نیازمند آزمون عملی:** روی VPS بررسی کن که HTTP عمومی روی پورت پنل وصل نمی‌شود، HTTPS ورود را انجام می‌دهد و SSH tunnel همچنان کار می‌کند. اگر از reverse proxy استفاده می‌کنی، باید HTTPS را به backend درست منتقل کند.
- **فایل‌ها:** `install.sh` و `src/main.rs` (تابع‌های `login` و راه‌اندازی Listenerها).

## ۲. بالا — محافظت از پورت‌های حیاتی با اعداد ثابت (اصلاح‌شده در 0.4.33)

- **شواهد:** در `src/main.rs`، توابع `valid_firewall_rule` و `firewall_rule_validation_error` فقط پورت‌های `22`، `8282` و `8443` را از تغییر قوانین مستثنا می‌کنند.
- **پیامد:** اگر SSH یا پنل روی پورت دیگری باشد، تغییر قانون فایروال ممکن است دسترسی به سرور را قطع کند.
- **تغییر:** پورت‌های ARG از bind جاری و پورت‌های SSH از خروجی مؤثر `sshd -T` استخراج می‌شوند و پورت‌های پیش‌فرض نیز fallback هستند. بازگردانی زمان‌دار در صورت تأییدنشدن اتصال هنوز پیاده‌سازی نشده است.
- **فایل:** `src/main.rs`.

## ۳. بالا — ترمینال Root بدون احراز هویت مجدد (اصلاح‌شده در 0.4.33)

- **شواهد:** در `frontend/src/TerminalPage.tsx` هشدار و دکمهٔ تأیید وجود دارد، اما `terminal_socket` در `src/main.rs` برای بازکردن ترمینال روت فقط معتبر بودن نشست مدیر را بررسی می‌کند.
- **پیامد:** در صورت دسترسی فرد غیرمجاز به نشست مدیر، امکان استفاده از قابلیت‌های روت فراهم است.
- **تغییر:** گذرواژهٔ مدیر دوباره بررسی می‌شود؛ مجوز یک‌بارمصرف ۶۰ثانیه‌ای به نشست و کاربر جاری وابسته است و تلاش ناموفق rate limit می‌شود. MFA و گزینهٔ غیرفعال‌سازی ترمینال روت هنوز وجود ندارد.
- **فایل‌ها:** `frontend/src/TerminalPage.tsx` و `src/main.rs`.

## ۴. بالا — ناهماهنگی وضعیت Update در مرورگر و سرور (اصلاح رابط در 0.4.32)

- **شواهد:** نسخهٔ بررسی‌شدهٔ `frontend/src/App.tsx` بعد از گذشت حدود ۱۰ دقیقه امکان گزارش «گیرکردن آپدیت» دارد، درحالی‌که `scripts/update-helper.sh` فرایند واقعی و قفل آپدیت را مستقل مدیریت می‌کند و Build ممکن است بیشتر طول بکشد.
- **پیامد:** نمایش خطای زودهنگام یا پیشنهاد تلاش مجدد در حالی که آپدیت واقعاً در حال اجرا است.
- **تغییر:** رابط دیگر پس از ۱۰ دقیقه عملیات را متوقف‌شده فرض نمی‌کند و وضعیت Helper/Job را دنبال می‌کند.
- **نیازمند آزمون عملی:** سناریوهای قطع اتصال، شکست Build، restart و Rollback روی سرور آزمایش نشده‌اند.
- **فایل‌ها:** `frontend/src/App.tsx`، `scripts/update-helper.sh` و `src/main.rs`.

## ۵. متوسط — امکان توقف سرویس‌های ضروری systemd (محدودشده در 0.4.33)

- **شواهد:** `run_service_operation` و `execute_service_request` در `src/main.rs` عملیات‌هایی مانند `stop`، `disable` و `mask` را برای سرویس‌های دارای نام معتبر مجاز می‌کنند.
- **پیامد:** اشتباه مدیر یا تصاحب نشست می‌تواند سرویس SSH، شبکه یا خود ARG را متوقف کند.
- **تغییر:** عملیات توقف، restart، disable و mask برای ARG، SSH و سرویس‌های اصلی شبکه رد می‌شوند؛ درخواست‌های مجاز همچنان در Audit ثبت می‌شوند. بازگشت زمان‌دار لازم نیست چون عملیات مخرب از API مسدود شده است.
- **فایل:** `src/main.rs`.

## ۶. متوسط — گستردگی عملیات پر‌دسترسی در Docker و فایل‌منیجر

- **شواهد:** `src/files.rs` و `src/docker.rs` عملیات مدیریتی را با بررسی نقش مدیر و اعتبارسنجی ورودی به Helper دارای دسترسی بالا می‌فرستند.
- **پیامد:** تصاحب نشست مدیر یا نقص احتمالی اعتبارسنجی می‌تواند بر فایل‌ها و سرویس‌های کل ماشین اثر بگذارد.
- **اصلاح پیشنهادی:** تست موارد Symlink، مسیرهای سیستمی و عملیات تخریبی؛ محدودیت منابع و هم‌زمانی؛ لاگ مقصد عملیات بدون ثبت اسرار؛ کاهش سطح دسترسی در حد امکان.
- **فایل‌ها:** `src/files.rs`، `src/docker.rs` و `src/main.rs`.

## اولویت اجرای اصلاحات

۱. آزمون استقرار محدودسازی HTTP و ورود HTTPS روی VPS و reverse proxy.

۳. احراز هویت مجدد برای Terminal Root.  
۴. یکپارچه‌سازی و تست واقعی Update، تشخیص شکست و Rollback.
