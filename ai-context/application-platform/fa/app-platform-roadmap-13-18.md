# نقشهٔ راه پلتفرم اپلیکیشن: فازهای ۱۳ تا ۱۸

این سند ادامهٔ برنامهٔ پلتفرم اپلیکیشن ARG تا مرحلهٔ انتشار است. وضعیت کد، تست مخزن و آزمون روی میزبان یا چند VPS از هم جدا ثبت می‌شوند. وجود صفحه یا جدول به‌تنهایی به معنی تکمیل فاز نیست.

## نقطهٔ فعلی

فازهای ۰۰ تا ۱۲ در [معماری پلتفرم اپلیکیشن](app-platform-architecture.md) آمده‌اند. این سند نقاط عطف قبلی و مرزهای پیاده‌سازی آن‌ها را ثبت می‌کند. فاز ۱۸ checkpoint سخت‌سازی است، نه پایان نقشه‌راه اصلی. ادامهٔ برنامه را در [فازهای ۱۸ تا ۴۸](app-platform-roadmap-18-48.md) ببین؛ شرح یک فاز به معنی پیاده‌سازی آن نیست.

## فاز ۱۳ — پایش و هشدار اپلیکیشن

### هدف

وضعیت واقعی فرایند اختصاصی و دادهٔ پایدار هر اپ را نشان بده؛ مصرف Nginx یا PHP-FPM مشترک، ترافیک کل سرور یا دیتابیس مشترک را به یک سایت نسبت نده.

### تحویل

- فقط سرویس‌های systemd تحت مدیریت ARG و مختص همان اپ نمونه‌برداری شوند. وضعیت فعال، شمارندهٔ تجمعی CPU، RAM جاری و آخرین اندازه‌گیری شناخته‌شدهٔ Volume ذخیره شوند.
- CPU از اختلاف دو شمارنده محاسبه شود. واحد نمایش «درصد یک هسته» باشد؛ عدد بالاتر از ۱۰۰٪ در VPS چند‌هسته‌ای معتبر است.
- تاریخچه با migration افزایشی SQLite، index اپ/زمان و پاک‌سازی رکوردهای منقضی‌شده نگه‌داری شود. سقف کار هر دور داشته باشد تا بازکردن صفحه پردازش سنگین ایجاد نکند.
- API خواندن پایش و ثبت آستانه با نقش مدیر، بررسی Origin برای نوشتن، اعتبارسنجی ورودی و Audit ارائه شود.
- بخش پایش در کارت محلی اپ به‌صورت بسته نمایش داده شود و فقط پس از بازشدن داده بگیرد. قدیمی، ناموجود و اندازه‌گیری‌نشده از هم متمایز باشند.
- هشدارهای یکتای باز/رفع‌شده برای توقف سرویس، CPU و RAM ثبت شوند. شبکه و latency HTTP تا زمان وجود منبع اندازه‌گیری مختص اپ، نامشخص بمانند.

### معیار پذیرش

۱. Migration روی دیتابیس جدید و موجود بدون تغییر داده‌های قبلی انجام شود.
۲. محاسبهٔ CPU با نمونهٔ مفقود، ریست شمارنده، فاصلهٔ صفر و فاصلهٔ زمانی زیاد مقدار ساختگی نسازد.
۳. نمونه‌برداری سقف داشته باشد، سرویس مشترک/پشتیبانی‌نشده را رد کند و پس از Restart ادامه یابد.
۴. اعتبارسنجی آستانه، مجوز، یکتایی/رفع هشدار، نگه‌داری تاریخچه و مسیر خطا تست شوند.
۵. Rust test/release build و Frontend check/build موفق باشند. برای تأیید systemd، روی میزبان آزمایشی بار معلوم ایجاد و شمارنده‌ها با سیستم مقایسه شوند.

### مرز فعلی پیاده‌سازی

کد فعلی sampler، تاریخچه و آستانه‌های SQLite، هشدارها، API مدیر و پنل بستهٔ هر اپ را اضافه می‌کند. در هر دقیقه حداکثر ۲۰ سرویس با قدیمی‌ترین نمونه بررسی و تاریخچهٔ ۳۰روزه نگه‌داری می‌شود. ترافیک مختص اپ، latency HTTP، آمار processهای Docker و تفکیک سرویس‌های مشترک در این مرحله وجود ندارد.

## فاز ۱۴ — شبکهٔ امن اپ بین VPSها

### هدف و طراحی

یک data plane خصوصی اختیاری بین نصب‌های جفت‌شدهٔ ARG ایجاد شود. ارتباط HTTPS مربوط به Federation فقط control plane است و نباید شبکهٔ خصوصی اپ معرفی شود.

### ترتیب تحویل

۱. ADR برای انتخاب WireGuard یا tunnel احراز‌شده بنویس: مالکیت/چرخش/ابطال کلید، route مجاز، MTU، NAT، رفتار قطع ارتباط و بازیابی گره خاموش.
۲. state machine همتا (`planned`, `provisioning`, `ready`, `degraded`, `revoked`, `failed`) و reconciliation job بساز. کلید عمومی و metadata امن ذخیره شود؛ کلید خصوصی فقط فایل root-only باشد و هیچ API آن را برنگرداند.
۳. پیش‌فرض deny باشد. مسیر اپ به peer و CIDR باید صریح و allowlist شود. هم‌پوشانی با شبکه میزبان، Docker، metadata و peerهای قبلی رد شود.
۴. سلامت handshake/latency/route با timeout محدود بررسی و تغییرات ممیزی شود. به مرورگر shell یا دستور route دلخواه نده.
۵. UI پس از اثبات ایجاد، بررسی، reconcile و حذف امن تونل فعال شود. دسترسی control plane از رسیدن data plane جدا نشان داده شود.

### معیار پذیرش

- تست helper برای permission فایل کلید، اعتبار CIDR، هم‌پوشانی route، ابطال، تکرارپذیری reconcile و رفتار deny-by-default.
- تست واقعی دو VPS برای اتصال peer، routeهای مجاز، بازیابی بعد Restart، قطع node، چرخش کلید و ابطال.
- صرف ارتباط API کنترل‌کننده نباید Badge «متصل» بسازد. تا آزمون دو میزبان، وضعیت این فاز طراحی یا آزمایشی باقی می‌ماند.

## فاز ۱۵ — ترمینال، فایل و سورس مختص اپ

### هدف

عملیات هر اپ از محدودهٔ خودش انجام شود؛ ترمینال Root و فایل‌منیجر سراسری سرور به‌عنوان ترمینال یا فایل‌منیجر مختص اپ استفاده نشوند.

### تحویل

- ترمینال اپ با هویت غیر root، مسیر کاری ثابت، سقف نشست و PTY، timeout بیکاری، محدودیت خروجی، مجوز صریح و Audit اجرا شود. دسترسی به secretهای ARG، اپ مجاور، اعتبارنامهٔ میزبان و مسیر مطلق دلخواه ممنوع باشد.
- فایل‌منیجر فقط releaseها و دادهٔ پایدار همان اپ را ببیند. مسیرها زیر ریشهٔ بازشده resolve شوند و traversal یا خروج symlink رد شود. ویرایش با ETag/نسخهٔ optimistic انجام شود.
- Release فعال تغییرناپذیر بماند. ویرایش زندهٔ آن خاموش باشد؛ تغییر باید در stage یا deployment جدید اعمال شود.
- نمای Git فقط repository، ref، commit pin‌شده و تاریخ Deploy را نشان دهد؛ credential یا private key ذخیره‌شده نمایش داده نشود.
- Upload/download جریانی، محدود از نظر حجم و قابل لغو باشند. حذف و تغییر مخرب نیازمند تأیید و Audit است.

### معیار پذیرش

Traversal، symlink race، دسترسی بین اپ‌ها، ETag قدیمی، قطع/اتصال مجدد PTY، خروجی حجیم، انقضای نشست، مجوز فایل و رد نقش غیرمدیر تست شوند. رفتار با user واقعی سرویس و layout واقعی روی میزبان جدا بررسی شود. Root terminal همچنان ویژگی جدا و خطرناک است.

## فاز ۱۶ — انتقال امن اپ بین VPSها

### هدف

انتقال به‌صورت Job قابل ادامه و اعتبارسنجی انجام شود؛ سرور مبدأ تا تأیید مقصد و cutover صریح، مرجع بازیابی باقی بماند.

### ماشین وضعیت

`draft → preflight → source_snapshot → transfer → restore → validate → cutover_pending → cutover → complete`، با وضعیت‌های نهایی `failed`, `cancelled`, `rolled_back`. هر گام پایدار و idempotent باشد.

### تحویل

- Preflight گراف وابستگی را بسازد: runtime، سرویس‌ها، دامنه/Nginx/TLS، Volume، دیتابیس، S3، پورت، زمان‌بندی و وابستگی خارجی.
- اپ بدون state فقط وقتی برای downtime کمتر مناسب باشد که runtime و health check مقصد تطبیق دارد. انتقال stateful به سازگاری داده، توقف نوشتن یا replication، هشدار downtime و backup/restore تأییدشده نیاز دارد.
- Manifest امضاشده و chunkهای checksumدار با حجم محدود از پروتکل احراز‌شدهٔ Node منتقل شوند؛ resume و cancel داشته باشند. Secret محیطی plaintext در log یا browser state نرود.
- مقصد در هویت جدید و staging domain/port restore شود. مالکیت فایل، سرویس، HTTP health و checkهای اپ بررسی شوند.
- Cutover صریح باشد. طبق برنامهٔ انتخابی مبدأ fence/فقط‌خواندنی یا متوقف بماند تا دو نویسنده هم‌زمان ایجاد نشوند. Rollback مسیر و وضعیت مبدأ را از state ثبت‌شده برگرداند.
- حذف مبدأ کار جداگانه‌ای پس از مهلت نگه‌داری و تأیید تازه باشد.

### معیار پذیرش

قطع/ادامه انتقال، عدم تطابق checksum، پرشدن دیسک، runtime متفاوت مقصد، شکست restore/health، درخواست تکراری cutover، fencing و rollback تست شوند. آزمون واقعی دو VPS برای اپ stateless و اپ stateful لازم است. تغییر metadata مالکیت، انتقال محسوب نمی‌شود.

## فاز ۱۷ — Webhook استقرار و Backup اپ

### Webhook امضاشده

- مسیر جدا برای GitHub/GitLab-style webhook با secret reference، HMAC روی raw body، مقایسهٔ constant-time، محافظ replay مبتنی بر timestamp و سقف حجم payload.
- Hook دقیقاً به یک اپ و repository/ref مجاز محدود شود. فقط Job استقرار موجود را Queue کند؛ متن shell اجرا نکند.
- پاسخ فقط شناسهٔ opaque درخواست/Job باشد. secret، payload کامل و مقدار env در Log نرود. چرخش/ابطال و نتیجهٔ تحویل Audit شود.

### پشتیبان‌گیری

- Manifest نسخه‌دار، metadata اپ، Release انتخابی، دادهٔ پایدار و snapshot دیتابیس پشتیبانی‌شده را مشخص کند. `.env` plaintext، credential و cache موقت پیش‌فرض خارج باشند.
- آرشیو پیش از انتقال رمز شود؛ کلید بازیابی در اختیار کاربر یا در مسیر root-only تأییدشده باشد. checksum و نسخهٔ schema/قالب همراه آن باشند. Export secret مسیر صریح و رمزگذاری‌شدهٔ جدا داشته باشد.
- Restore ابتدا به هویت staging تازه انجام شود. یکپارچگی آرشیو، مسیر، مالکیت، runtime، سازگاری دیتابیس و health پیش از cutover بررسی شوند.
- Job زمان‌بندی‌شده concurrency و retention محدود داشته باشد و آخرین موفقیت/کهنگی را نشان دهد. Upload موفق به‌تنهایی اثبات پشتیبان قابل‌بازیابی نیست؛ restore drill لازم است.

### معیار پذیرش

اعتبار HMAC، جلوگیری از replay، رد ref نامعتبر و صف‌بندی idempotent بررسی شوند. Backup رمز‌شده در محیط پاک restore شود؛ کلید گمشده، آرشیو خراب، دیسک کم، لغو، retention و upload ناقص تست شوند. Backup تنها پس از تست restore «تأییدشده» است.

## فاز ۱۸ — سخت‌سازی انتشار و تکمیل

### شواهد لازم برای Release

- بازبینی threat model برای Federation، helper، sandbox build، ترمینال اپ، secretهای S3، webhook، کلید backup، دسترسی فایل و cutover مهاجرت.
- تست خودکار Rust، type-check/build فرانت‌اند، build مستندات، migration از schemaهای پشتیبانی‌شده و allowlist helper.
- ماتریس نسخه‌های Debian/Ubuntu و سرویس‌های اختیاری Nginx، Docker، PHP، Node، MySQL و Providerهای S3. نبود سرویس اختیاری باید graceful باشد.
- اجرای روی میزبان آزمایشی برای نصب/آپدیت/rollback، Nginx/PHP-FPM، Node/systemd، فشار دیسک، backup/restore و بازیابی لغو/Restart.
- گردش چند VPS برای pairing، overlay، انتقال اپ، قطع node، revocation و ناسازگاری پروتکل. ویژگی چندسروری بدون دست‌کم دو VPS مستقل production-ready نیست.
- سنجش کارایی در VPSهای نماینده: جابه‌جایی صفحه اسکن سنگین راه نیندازد و نمونه‌برداری/Job سقف concurrency، CPU، RAM، I/O و retention داشته باشند.
- مستندات فارسی و انگلیسی، runbook شکست، راهنمای migration/rollback و changelog؛ افزایش نسخه فقط پس از عبور از دروازه‌های در دسترس.

### قاعدهٔ اعلام تکمیل

برای هر ویژگی وضعیت‌های `پیاده‌سازی‌شده`، `تست خودکار موفق`، `تست میزبان موفق` و `تست چندمیزبانه موفق` جدا ثبت شوند. آن‌ها را به یک برچسب کلی «کامل» تبدیل نکن. ویژگی‌ای که دروازهٔ ایمنی‌اش باز است باید غیرفعال یا صریحاً آزمایشی باشد.

## روش اجرای بسته‌ها

اجرا از فاز ۱۸ تا ۴۸ در بسته‌های پنج‌فازی ادامه دارد. در هر بسته کد موجود بررسی، قابلیت محدود پیاده‌سازی، هر دو نقشه‌راه و changelog به‌روز، تست و build محلی اجرا و در صورت وجود زیرساخت آزمایشی، تست میزبان/چندمیزبانه انجام می‌شود؛ سپس تغییرات روی `development` commit و push می‌شوند. گیت بیرونیِ اجرا‌نشده باید Pending بماند و قبولی فاز ۴۸ آخرین دروازهٔ انتشار است.
