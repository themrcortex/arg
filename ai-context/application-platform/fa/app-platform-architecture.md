# معماری پلتفرم اپلیکیشن

این سند baseline فاز ۰۰ و تصمیم‌های معماری لازم برای گسترش ARG از مدیریت میزبان به مدیریت چرخهٔ عمر اپلیکیشن را ثبت می‌کند. این متن وضعیت فعلی مخزن و محدودیت‌هایی را که فازهای بعدی باید حفظ کنند توضیح می‌دهد؛ قابلیت برنامه‌ریزی‌شده به معنی انتشار آن نیست.

## خط پایهٔ مخزن و قابلیت‌های افزوده‌شده

ARG یک سرویس مستقل Rust/Axum با رابط React/TypeScript/Vite است. خروجی Frontend داخل باینری Release قرار می‌گیرد. SQLite حساب‌های پنل، نشست‌ها، تنظیمات، Audit، نمونه‌های مانیتورینگ و metadata قابلیت‌ها را نگه می‌دارد. عملیات نیازمند دسترسی بالاتر از مرز Unix socket خصوصی به Helper محدودشده عبور می‌کنند.

موجودی اولیهٔ فاز ۰۰ ماژول‌های `src/federation.rs`، `src/nginx.rs`، `src/docker.rs`، `src/s3/`، `src/files.rs`، `src/metrics.rs` و `src/maintenance.rs` را پوشش می‌داد. Federation امکان جفت‌کردن ARGها، خواندن وضعیت و سرویس‌های راه‌دور و proxy کردن فضای‌کار احراز‌شده به Node انتخاب‌شده را دارد. سایت‌های Nginx، منابع Docker و Bucketهای S3 همچنان منابع همان سروری هستند که روی آن قرار دارند. فازهای ۰۳ تا ۰۸ از آن زمان Registry اپلیکیشن، موتور Deploy پایدار، مدیریت Runtime، Runner لاراول، Runner مربوط به Node.js و انتشار Static/SSR را افزوده‌اند؛ مرز دقیق قابلیت‌های موجود در جدول وضعیت فازها آمده است.

bootstrap دیتابیس SQLite در `src/main.rs` باقی است؛ کد دامنهٔ اپ، Deploy، Runtime، Laravel و Node به‌ترتیب در `src/apps.rs`، `src/deploy.rs`، `src/runtimes.rs`، `src/laravel.rs` و `src/node.rs` تفکیک شده است. تغییرات schema آینده باید migration افزایشی و idempotent باشند و داده‌های کاربران، نشست‌ها، Nodeها، S3، Nginx، Docker و اپلیکیشن‌ها را حفظ کنند. نسخهٔ پروتکل Federation Node فعلی `arg-node/2` است؛ هر تغییر سازگاری پروتکل باید جداگانه بررسی شود.

ARG باید روی یک VPS بدون Node جفت‌شده و بدون Docker همچنان کامل و مفید باشد. وابستگی‌های اختیاری نباید اجباری شوند. نبود Docker، PHP، Node.js، S3 یا قابلیت شبکه باید صادقانه `در دسترس نیست` نشان داده شود، نه وضعیت سالم ساختگی.

## تصمیم معماری: کنترل محلی و سرورهای راه‌دور

### تصمیم

هر نصب ARG کنترل‌سنتر مستقل و کامل میزبان خودش باقی می‌ماند. یک ARG جفت‌شده می‌تواند از طریق درخواست‌های Federation احراز‌شده و دارای scope مشخص مدیریت شود. در شروع، وقتی ARG روی VPS مقصد نصب است، بستهٔ Agent جداگانه لازم نیست.

پنل کنترل مسیر درخواست را فراهم می‌کند؛ سروری که مالک منبع است همچنان منبع حقیقت آن منبع می‌ماند. Controller فقط metadata جفت‌شدن و دادهٔ راه‌دوری را که برای مسیریابی یا خلاصهٔ صریحاً «آخرین وضعیت شناخته‌شده» لازم است نگه می‌دارد. دادهٔ Node نباید بی‌صدا کپی یا cache کهنه به‌عنوان زنده نمایش داده شود.

### هویت و نام‌ها

هر نصب شناسهٔ تغییرناپذیر `server_uuid` دارد. hostname سیستم فقط metadata مشاهده‌شده است؛ هویت شبکه نیست و ARG نباید ضمن یک عملیات دیگر آن را تغییر دهد. `public_name` نام مدیریتی است که به Nodeهای جفت‌شده اعلام می‌شود. `local_label` نام مستعار محلی همان Controller است و به Nodeهای دیگر ارسال نمی‌شود. UI باید دقیقاً بگوید کدام نام تغییر می‌کند و مقصد عملیات را پیش از هر Write نمایش دهد.

Pairingهای قبلی با migration افزایشی و بدون تغییر Node ID یا باطل‌کردن اعتبارنامهٔ سالم حفظ می‌شوند. Handshake پروتکل v2 اکنون UUID پایدار سرور و نام عمومی را به‌صورت اختیاری منتقل می‌کند و یک endpoint احراز‌شده تغییر نام عمومی را با پنل‌های جفت‌شده همگام می‌کند. Nodeهای قدیمی تا زمان اعلام UUID پایدار با کلید فضای‌کار `legacy:<local-id>` کار می‌کنند. برچسب محلی Controller جدا می‌ماند و به Nodeها ارسال نمی‌شود.

### وضعیت پیاده‌سازی فاز ۰۱

- UUID نصب‌های جدید هنگام نیاز در تنظیمات SQLite ذخیره می‌شود؛ فیلدهای هویت به Pairingهای فعلی افزوده می‌شوند و Pairing دوباره ساخته نمی‌شود.
- نام عمومی سرور مستقل از hostname سیستم تنظیم می‌شود. Controller دریافت‌کننده برچسب محلی خودش را جدا نگه می‌دارد.
- حالت تک‌سرور و چندسرور ترجیح رابط هستند و تغییرشان Pairing را حذف نمی‌کند. حالت چندسرور گزینه‌های سرور محلی، نمای خواندنی همهٔ سرورها و فضای‌کار Nodeهای راه‌دور را دارد.
- انتخاب فضای‌کار راه‌دور در `sessionStorage` ذخیره و با UUID پایدار مسیریابی می‌شود. انتخاب عددی قبلی هنگام بارگذاری فهرست Nodeها مهاجرت می‌کند؛ Nodeهای قدیمی کلید legacy مشخص دارند. خروج از حساب فضای‌کار فعال را پاک می‌کند و سوییچ مقصد cache سنگین را پاک می‌کند.
- Routeهای proxy فضای‌کار و ترمینال فقط UUID معتبر یا کلید legacy صریح را می‌پذیرند. Routeهای مدیریت Node همچنان شناسهٔ عددی محلی دارند.
- تغییر نام عمومی با کانال Federation احراز‌شدهٔ HTTPS به سرورهای جفت‌شده ارسال می‌شود؛ قطع ارتباط بخشی به مدیر گزارش می‌شود.
- نمای همهٔ سرورها هر Node راه‌دور را هنگام درخواست بررسی می‌کند، شکست اتصال را «در دسترس نیست» نشان می‌دهد و پیش از مدیریت به انتخاب صریح فضای‌کار نیاز دارد. هنگام شکست هیچ عملیاتی به سرور دیگری منتقل نمی‌شود.
- تست migration و route فاز ۰۱ اضافه شده است. برای اجرای تست Rust، محیطی با Rust toolchain و فرمان `cargo test --locked` لازم است.

### وضعیت پیاده‌سازی فاز ۰۲

- نقش‌ها `standalone`، `member`، `controller-capable` و `both` هستند. تغییر نقش با تأیید انجام می‌شود و اگر باعث یتیم‌شدن Node یا Controller جفت‌شده شود، تعداد وابستگی‌ها گزارش و عملیات متوقف می‌شود.
- کد اتصال یکی از دو سطح فقط‌خواندنی یا کامل را صادر می‌کند. سرور مقصد scope هر Controller را ذخیره و برای هر درخواست بررسی می‌کند؛ Controller نیز پیش از route کردن درخواست مجوز اعطاشده را کنترل می‌کند.
- مقصد روی نشست‌های فضای‌کار راه‌دور guard اعمال می‌کند. خواندن، نوشتن، ترمینال و اجازهٔ ورود به Root Terminal scopeهای جدا دارند. نشست قدیمی به‌جای حفظ دسترسی کامل مدیر، با scope فقط‌خواندنی مهاجرت می‌شود.
- نسخهٔ قابلیت‌ها هنگام جفت‌سازی مذاکره می‌شود. Node قدیمی یا فاقد قابلیت proxy/terminal در وضعیت legacy و فقط‌خواندنی مشخص می‌ماند و عملیات ناسازگار پاسخ `Upgrade Required` می‌گیرد.
- کلید Controller با فایل pending امن و retry idempotent چرخانده می‌شود. نشست فضای‌کار پس از ۱۲ ساعت منقضی و پیش از استفاده تمدید می‌شود. لغو اتصال Controller، نشست‌های راه‌دور همان Controller را هم حذف می‌کند.
- درخواست‌های راه‌دور HTTPS با اعتبارسنجی گواهی، redirect خاموش، timeout محدود، کنترل DNS و pin کردن IP resolve‌شده در درخواست‌های HTTP اجرا می‌شوند. مقصد private به انتخاب صریح نیاز دارد؛ loopback، link-local و آدرس metadata همیشه رد می‌شوند.
- وضعیت‌های `healthy`، `degraded`، `offline`، `untrusted` و `incompatible` به همراه زمان بررسی و خطای پاک‌سازی‌شده ذخیره می‌شوند. Write راه‌دور در مقصد با نام Controller جفت‌شده Audit می‌شود.
- تست‌های Rust شاخهٔ `development` شامل نقش/scope، مجوز نشست، تشخیص آدرس خصوصی، اعتبارسنجی endpoint و migration هستند. برای ادعای پوشش end-to-end هنوز اجرای واقعی بین دو VPS و TLS لازم است.

### وضعیت پیاده‌سازی فاز ۰۳

- Registry اپلیکیشن با UUID، مالکیت سرور، قالب و نوع منبع، برچسب، دامنه، رزرو پورت، وضعیت هدف/مشاهده‌شده، آرشیو نرم و شمارهٔ نسخه برای کنترل ویرایش هم‌زمان اضافه شده است.
- جدول جداگانهٔ `application_services` برای adapterهای پردازش/منبع در فازهای بعد ساخته می‌شود؛ هنوز API اجرای سرویس نیست.
- صفحهٔ اپلیکیشن‌ها مدیریت محلی و تجمیع خواندنی Nodeهای آماده را دارد. خطای VPS خاموش جداگانه نشان داده می‌شود و تغییر از فضای‌کار میزبان انجام می‌شود.
- بررسی دامنه با رکوردهای فعال ARG و `server_name` زندهٔ Nginx از مسیر helper انجام می‌شود. اگر Nginx نصب باشد ولی قابل بررسی نباشد، ثبت دامنه رد می‌شود. پورت TCP با رزروهای ARG و جدول listenerهای کرنل بررسی می‌شود.
- این Registry سورس دریافت نمی‌کند، Build/Deploy انجام نمی‌دهد، Runtime نصب نمی‌کند، Secret نمی‌سازد و سرویس را Running نشان نمی‌دهد. `observed_state` تا پیاده‌سازی adapter واقعی `unknown` باقی می‌ماند.
- migration افزایشی و تست‌های اعتبارسنجی با `cargo test --locked` گذشتند؛ type-check/build فرانت‌اند و بررسی مستندات نیز موفق بود. تست واقعی چند VPS هنوز لازم است.

| ۲۵ — Preview و Snapshot | فقط Snapshot متادیتا | Snapshot تنظیمات اپ/محیط hashدار است و مقدار Secret ندارد؛ چرخه Preview، approval، بازیابی/ارتقا و جداسازی داده هنوز باز است. |
| ۲۶ — Orchestration در Compose | فقط لینک metadata | مدیر می‌تواند کانتینر موجود Docker را برای نمایش وضعیت به اپ Docker وصل کند؛ حذف لینک Docker را تغییر نمی‌دهد. کنترل و reconcile Compose و rollback باز است. |
| ۲۷ — DNS Provider | adapter جزئی Cloudflare | Credential رمز‌شده، بررسی Zone و API محدود A/AAAA/CNAME/MX/TXT/CAA/SRV اضافه شده؛ Route53/DO، propagation، DNS-01 و تست ارائه‌دهنده باقی است. |
| ۲۸ — Domain/SSL/Nginx | پیوند مالکیت metadata، جزئی | اپ دارای دامنه می‌تواند فقط به سایتی وصل شود که دامنه‌اش دقیقاً در `server_name` است؛ این API پیکربندی را تولید یا reload نمی‌کند. مدیریت کامل SSL، performance و rollback باز است. |
| ۲۹ — PostgreSQL | inventory فقط‌خواندنی | نسخهٔ `psql`، unit و `pg_isready` با timeout محدود نمایش داده می‌شود؛ نصب، SQL، نقش‌ها، backup و مدیریت دیتابیس وجود ندارد. |
| ۳۰ — پشتیبان و بازیابی | آرشیو سورس محدود | آرشیو ZIP از release فعال با سقف حجم، hash و حذف dotfile/runtime ساخته و دانلود می‌شود؛ دیتابیس، secrets و فایل‌های persistent را ندارد و قابل restore نیست. |
| ۳۱ — ناوگان و rollout | برچسب و پیش‌نمایش | Tagهای Node و طرح rollout با canary ذخیره می‌شوند؛ build/update یا rollback راه‌دور اجرا نمی‌شود. |
| ۳۲ — شبکهٔ خصوصی | پیش‌نویس policy | metadata اتصال اپ به سرویس Node ثبت و حذف می‌شود؛ WireGuard، route و firewall پیاده نشده‌اند و `enforced=false` می‌ماند. |
| ۳۳ تا ۴۸ — ادامهٔ نقشه‌راه | برنامه‌ریزی‌شده | جزئیات در نقشه‌راه کامل است؛ ادعای قابلیت تولیدی به تست میزبان/ناوگان نیاز دارد. |

«کامل» یعنی پیاده‌سازی مخزن و تست خودکار همان فاز موجود است؛ به معنی آزمون واقعی Federation چند VPS، مرجع صدور گواهی، APT، MySQL یا systemd روی VPS عملیاتی نیست.

### وضعیت پیاده‌سازی فاز ۰۴

- Jobهای Deploy وضعیت و گام‌ها را نگه می‌دارند و برای بازیابی از lease و heartbeat استفاده می‌کنند؛ وضعیت به طول عمر درخواست مرورگر وابسته نیست.
- دریافت Git، ZIP و پوشهٔ مجاز اعتبارسنجی و محدودیت دارد. Releaseها جداگانه staging می‌شوند، از طریق اشاره‌گر اتمی `current` فعال می‌شوند و نسخه‌های جاری/قبلی نگه‌داری می‌شوند.
- لغو، retry، بازیابی پس از restart، rollback، pin کردن source و پاک‌سازی از API ممیزی‌شده و با کنترل مالکیت اپ انجام می‌شوند.
- تست مخزن رفتار Job قطع‌شده و اشاره‌گر Release را پوشش می‌دهد؛ کمبود دیسک و crash روی میزبان واقعی هنوز تست یکپارچگی می‌خواهد.

### وضعیت پیاده‌سازی فاز ۰۵

- inventory، نسخه‌های PHP CLI/FPM، Composer، Node.js و package managerها، Nginx و Docker را همراه اطلاعات preflight میزبان گزارش می‌کند.
- عملیات بسته‌های APT پیش از تغییر، شبیه‌سازی اثر را نشان می‌دهند. ARG مخزن ثالث تأییدنشده اضافه نمی‌کند و installer راه‌دور را با shell اجرا نمی‌کند.
- ترجیح Runtime و نسخهٔ build اپ جدا ذخیره و با نسخه‌های نصب‌شده اعتبارسنجی می‌شود؛ نبود Runtime اختیاری صریح نشان داده می‌شود.
- تست‌ها parsing inventory و اعتبارسنجی ترجیح نسخه را می‌پوشانند. نصب/حذف بسته باید قبل از عرضه روی Debian/Ubuntu جداشده آزمایش شود.

### وضعیت پیاده‌سازی فاز ۰۶

- بازرسی سورس Laravel، بررسی نیاز PHP، نگه‌داری `.env` و `storage`، نصب Composer از lockfile، پنهان‌سازی مقادیر محیط و اجرای allowlist مربوط به Artisan پیاده شده‌اند.
- فعال‌سازی وب pool مستقل PHP-FPM و سایت مدیریت‌شدهٔ Nginx می‌سازد، هر دو تنظیم را تست می‌کند و در شکست، تنظیم قبلی را برمی‌گرداند. ساخت دیتابیس MySQL کاربر مختص اپ با مجوز محدود به همان دیتابیس می‌سازد و رمز تصادفی را فقط در فایل محیط خصوصی اپ نگه می‌دارد.
- Queue، Scheduler، Horizon، Reverb و Octane از قالب‌های ثابت systemd استفاده می‌کنند. Reverb/Octane فقط روی loopback گوش می‌دهند؛ Octane مسیر upstream سایت را در Nginx تغییر می‌دهد و هنگام خاموش‌شدن به PHP-FPM برمی‌گرداند.
- Deploy و rollback دستی، وب و سرویس‌های فعال Laravel را تازه‌سازی می‌کنند و در شکست برای بازگشت به Release/runtime قبلی تلاش می‌کنند. این کار migration دیتابیس را برعکس نمی‌کند.
- تغییرات فعلی تشخیص خودکار نسخهٔ «system» برای PHP-FPM، بررسی تعارض سرویس/پورت، پاک‌سازی کاربر MySQL نیمه‌ساخته و بازیابی امن Release را تکمیل می‌کنند. ۱۰۵ تست Rust، `cargo build --locked --release`، type-check و build تولیدی Frontend موفق‌اند. رفتار واقعی Nginx، MySQL و systemd همچنان به VPS آزمایشی نیاز دارد.

### وضعیت پیاده‌سازی فاز ۰۷

- پروژهٔ Node از `package.json` و دقیقاً یک lockfile پشتیبانی‌شده بازرسی می‌شود. npm، pnpm و Yarn Classic در حالت نصب قابل‌تکرار اجرا می‌شوند؛ مدیر بستهٔ متعارض یا پشتیبانی‌نشده صریحاً رد می‌شود. وجود `scripts.start` ضروری و `scripts.build` اختیاری است.
- نصب dependency و build فقط هنگام Deploy اپ Node و در unit موقت systemd اجرا می‌شوند؛ DynamicUser، فضای موقت خصوصی، filesystem محدود، سقف ثابت منبع/زمان/خروجی و نبود دسترسی به دادهٔ خصوصی ARG اعمال می‌شود.
- هر اپ Node یک unit مشتق از UUID، فایل `.env` خصوصی، mount فقط‌خواندنی release/محیط، گروه اختصاصی، مسیر نوشتنی `shared/data`، میزبان/پورت loopback، سقف منابع، restart در شکست و مهلت توقف تمیز دارد. API مقدار secret را بازخوانی نمی‌کند.
- پیش از موفقیت، listener واقعی فقط روی loopback بررسی و درخواست HTTP فرستاده می‌شود. با ثبت دامنه، reverse proxy جداگانهٔ تحت مالکیت ARG تنها پس از بررسی تعارض ساخته می‌شود؛ سایت نامرتبط یا دستی‌تغییریافته بازنویسی نمی‌شود. صدور گواهی یک اقدام جدا در صفحهٔ Nginx است.
- Deploy و rollback فقط سرویسی را restart می‌کنند که قبلاً فعال بوده است. شکست فعال‌سازی تلاش می‌کند اشاره‌گر و وضعیت سرویس قبلی را بازگرداند. این عملیات اثر خارجی یا migration دیتابیس اپ را برعکس نمی‌کند.
- دروازهٔ خودکار فاز شامل ۱۱۵ تست Rust و type-check/build فرانت‌اند بود. build انتشار و مستندات نیز در بررسی نهایی همین فاز اجرا می‌شوند. اجرای واقعی npm، lifecycle پردازش systemd و Nginx به VPS آزمایشی Debian/Ubuntu نیاز دارد و با تست واحد ادعا نمی‌شود.

### وضعیت فاز ۰۸ — انتشار سایت‌های Static و SSR

- قالب‌های `auto`, `static`, `react`, `vue`, `vite`, `node`, `next` و `nuxt` در Registry ذخیره می‌شوند. تشخیص خودکار از manifest استفاده می‌کند؛ انتخاب دستی نوع انتشار را override می‌کند.
- React/Vue/Vite و فایل‌های آماده خروجی دارای `index.html` را بدون process وب Node از طریق Nginx منتشر می‌کند. مسیر خروجی، SPA fallback و پیکربندی cache در مشخصات اپ ذخیره می‌شوند. خروجی build محدود و پیش از انتشار بررسی می‌شود.
- متغیرهای Build فقط با پیشوند عمومی framework در SQLite ذخیره و فقط به مرحلهٔ build می‌رسند؛ محدودیت ۱۶ KiB و منع نام‌های secret-like اعمال می‌شود. UI هشدار می‌دهد مقدارها ممکن است به bundle عمومی راه پیدا کنند. متغیرهای Runtime در فایل خصوصی جدا باقی می‌مانند.
- Next.js/Nuxt و Node عمومی به مسیر SSR می‌روند. Next CLI استاندارد و Nuxt `.output/server/index.mjs` پشتیبانی می‌شوند؛ متغیرهای NITRO به loopback تنظیم شده و سرویس systemd محدود و وابسته به enable صریح باقی می‌ماند.
- فایل سایت Static با نام مختص اپ ساخته می‌شود؛ دامنهٔ موجود متعلق به سایت دیگر overwrite نمی‌شود. شکست تنظیم Nginx باعث بازگرداندن pointer می‌شود. Deploy و rollback مسیر root Nginx را با خروجی Release منتخب همگام می‌کنند.
- تست خودکار پوشش تشخیص Static در برابر SSR، خروجی آماده در ریشه/پوشه، path traversal، Nuxt entrypoint، تنظیمات SPA fallback و ruleهای Nginx را دارد. اجرای واقعی Debian/Ubuntu با Nginx و systemd جداگانه لازم است.

### مرز پیاده‌سازی فازهای ۰۹ تا ۱۲

- شبکه‌ها محلی همین سرورند. Docker bridge با `--internal` ساخته و با شناسهٔ ARG برچسب‌گذاری می‌شود. Helper فقط کانتینری را وصل می‌کند که برچسب `com.arg.application_id` آن با اپ انتخابی برابر باشد. سرویس native Node تنها endpoint پورت loopback ثبت‌شده را دریافت می‌کند؛ این metadata کشف سرویس است، نه جداسازی شبکه.
- دادهٔ پایدار Node در `/var/lib/arg/deployments/apps/<app-id>/shared/data/volumes/<name>` می‌ماند و داخل sandbox سرویس در `/shared/data/volumes/<name>` دیده می‌شود. اسکن فقط با درخواست کاربر و با سقف ۱۰۰هزار ورودی انجام می‌شود. جداکردن رکورد فایل را نگه می‌دارد؛ پاک‌سازی تأیید جدا می‌خواهد و فایل‌سیستم mount‌شده را رد می‌کند. سقف ثبت‌شده توسط kernel enforce نمی‌شود.
- S3 Binding به Bucket و prefix موجود در ARG اشاره می‌کند و secret را بازنمی‌گرداند. Prefix و سطح دسترسی metadata هستند؛ مرز واقعی مجوز باید در کلید یا policy ارائه‌دهنده تنظیم شود. Bucket تا وقتی اپ به آن متصل است قطع نمی‌شود.
- خروجی پردازش Node در journal سیستم‌عامل ثبت می‌شود. API حداکثر ۵۰۰ خط می‌خواند و با cursor ادامه می‌دهد. retention از سیاست سراسری میزبان می‌آید و ARG سوییچ per-app ساختگی ارائه نمی‌کند. این فاز برای Docker، Nginx، Jobها یا انتقال S3 collector جداگانه نمی‌سازد.
- تست‌های مخزن کد و migration را اعتبارسنجی می‌کنند. جداسازی شبکه Docker، permission گروه، رفتار cursor و چرخهٔ واقعی فایل باید روی میزبان آزمایشی Debian/Ubuntu هم بررسی شود.

### نقشهٔ راه فازهای ۱۳ تا ۴۸

ترتیب اجرا، مرز API و وضعیت، دروازه‌های پذیرش و تست‌های بیرونی در [نقشهٔ راه فازهای ۱۳ تا ۱۸](app-platform-roadmap-13-18.md) و [نقشهٔ راه فازهای ۱۸ تا ۴۸](app-platform-roadmap-18-48.md) ثبت شده‌اند. جدول وضعیت، کار مخزن را از تست میزبان و چند میزبان جدا می‌کند.

### واژگان و مالکیت

| اصطلاح | معنی |
| --- | --- |
| سرور | یک نصب ARG و میزبان Linux تحت مدیریت آن؛ شناسهٔ پایدار `server_uuid`. |
| Controller | نصب ARG که به سرور جفت‌شده درخواست احراز‌شده می‌فرستد. |
| سرور مدیریت‌شونده | نصب مقصد که هویت Controller را بررسی و درخواست محدود را محلی اجرا می‌کند. |
| فضای‌کار | context درخواست/رابط: سرور محلی یا یک سرور راه‌دور که صریحاً انتخاب شده است. |
| Application | پروژهٔ قابل استقرار که دقیقاً یک سرور مالک آن است. |
| Service | پردازش یا Container متعلق به اپ؛ مانند web، worker یا database. |
| Environment | محدودهٔ تنظیمات اپ مانند development، staging یا production. |
| Resource adapter | اتصال کنترل‌شده به منبع موجود میزبان، مانند Nginx، Docker، systemd، دیتابیس یا S3. |

یک سایت Nginx یا Container می‌تواند به Application متصل شود، ولی نباید دوباره ساخته یا بی‌اجازه تحت مالکیت ARG قرار گیرد. واردکردن منبع موجود نیازمند پذیرش صریح مالکیت و بررسی تعارض است.

### مسیریابی و مجوز

- هر خواندن یا نوشتن راه‌دور `server_uuid` مقصد مشخص دارد؛ انتخاب فضای‌کار به‌تنهایی مجوز نیست.
- «همهٔ سرورها» نمای تجمیعی/خواندنی است. تغییر از این صفحه باید مقصد مشخص بخواهد.
- Controller کاربر را محلی احراز می‌کند، اما سرور مقصد باید اعتبارنامه، عامل، قابلیت، scope و عملیات را مستقلاً بررسی کند.
- کد مرورگر نباید توکن خام Federation یا اعتبارنامهٔ فضای‌کار راه‌دور را دریافت یا ذخیره کند.
- توکن Controller عمر محدود و rotation دارد، لغو آن فوری است و مقصد Audit را ثبت می‌کند. نشست فضای‌کار پس از ۱۲ ساعت منقضی می‌شود و از کانال احراز‌شدهٔ Controller تمدید می‌شود؛ کلید pending برای retry rotation روی دیسک امن Controller می‌ماند.
- مذاکرهٔ پروتکل قابلیت‌ها و بازهٔ نسخه را اعلام می‌کند. اگر سازگاری امن احراز نشد، عملیات unavailable است؛ نباید بی‌صدا به عملیات گسترده‌تر تنزل کند.
- درخواست راه‌دور محدودیت اندازه و زمان، idempotency برای write قابل‌تکرار و خطای ساختاریافته دارد. Stream باید backpressure و لغو داشته باشد.

### مرز دسترسی ریشه

مرورگر ← API احراز‌شدهٔ Axum ← عملیات دامنه‌ای اعتبارسنجی‌شده ← Helper محدود روی Unix socket، فقط وقتی root لازم است. کد پروژه و فرمان‌های Build ورودی غیرقابل‌اعتمادند؛ باید با کاربر غیرریشهٔ اختصاصی اپ و context محدود اجرا شوند و هرگز به شکل shell string ساخته‌شده توسط کاربر به Helper privileged داده نشوند. Helper نیز عملیات ساختاریافته و allowlist را جداگانه اعتبارسنجی می‌کند.

### مالکیت Application و Job

هویت اپ و وضعیت Deploy را سروری نگه می‌دارد که اپ روی آن اجرا می‌شود. Controller می‌تواند درخواست را route کند، ولی نباید یک نسخهٔ authoritative دوم بسازد. عملیات طولانی Job پایدار با مقصد، عامل، state، Log محدود، رفتار لغو، idempotency و بازیابی پس از restart هستند. UI وضعیت را از Job و مشاهدهٔ واقعی میزبان می‌گیرد، نه از عمر HTTP request.

### ذخیره‌سازی و مهاجرت

- دادهٔ پایدار scope سرور دارد. تغییر فضای‌کار فایل، Volume، دیتابیس یا Secret را جابه‌جا نمی‌کند.
- S3 فضای Object است. Mount لایهٔ سازگاری اختیاری است و تضمین POSIX ندارد؛ فایل دیتابیس و کاری که قفل POSIX لازم دارد نباید روی Mount S3 قرار گیرد.
- انتقال اپ بین سرورها تغییر یک شناسه نیست: preflight، snapshot، انتقال، restore، verify، cutover و پاک‌سازی گام‌های مستقل‌اند.
- تضمین rollback در مرز cutover تعریف می‌شود. پس از پذیرفتن write در مقصد، بازگشت به مبدأ ممکن است writeها را از دست بدهد، مگر reverse sync یا پنجرهٔ maintenance در نظر گرفته شده باشد.
- migrationهای SQLite افزایشی، idempotent، با backup پیش از تغییر پرخطر و آزمون روی دیتابیس تازه و موجود هستند؛ داده‌های نامرتبط ARG را حفظ می‌کنند.

## Gate فازها و ماتریس تست

در دروازهٔ هر فاز، baseline قابل‌تکرار برای Frontend، Rust، Shell، مستندات و هماهنگی نسخه اجرا کن. نتیجهٔ هر فاز و محدودیت تست میزبان در جدول وضعیت بالا ثبت می‌شود. تست خودکار جای تست واقعی ارتباط دو VPS را نمی‌گیرد.

| محیط | پوشش لازم |
| --- | --- |
| یک VPS بدون Docker | سازگاری نصب/ارتقا، مدیریت محلی، عدم وابستگی پنهان به Node راه‌دور. |
| یک VPS با Docker و Runtimeها | مالکیت منابع، وضعیت سرویس، Storage، Log و نبود وابستگی اختیاری. |
| دو VPS جفت‌شده | Pair، سوییچ فضای‌کار، مسیریابی، revoke، همگام‌سازی هویت و Audit دوطرفه. |
| VPS راه‌دور خاموش | برچسب stale، timeout، retry، منع write مبهم و بازیابی پس از اتصال. |
| عملیات قطع‌شده یا کمبود دیسک | بازیابی Job، لغو، مرز rollback و حفظ اطلاعات کاربر. |
| نسخه‌های متفاوت پروتکل | مذاکرهٔ قابلیت، وضعیت unsupported و نبود fallback ناامن. |

هر فاز باید تست همان رفتار را اضافه کند؛ ماتریس نهایی جایگزین تست مرحله‌ای نیست. عملیات حساس به امنیت باید در مرز API هم تست مجوز داشته باشد، نه فقط در UI.

## موجودی Phase 00 مخزن

- **Backend:** Rust/Axum. ثبت Route در `src/routes.rs` است؛ ماژول‌های دامنه شامل Federation، Nginx، Docker، S3، Files، MySQL، Metrics و Maintenance هستند.
- **Frontend:** React، TypeScript، Vite، Tailwind و اجزای Radix/shadcn. ناوبری در `frontend/src/navigation.ts` و Shell در `frontend/src/App.tsx` است.
- **Persistence:** bootstrap دیتابیس SQLite در `src/main.rs` است؛ migration اپلیکیشن در `src/apps.rs` جدا شده و هنگام راه‌اندازی فراخوانی می‌شود.
- **دسترسی privileged:** سرویس ARG از Unix socket خصوصی با `arg-privileged.service` حرف می‌زند. هیچ قابلیتی نباید آن را به runner عمومی root تبدیل کند.
- **Federation:** پروتکل v2 و proxy فضای‌کار API/Terminal دارد. نقش سرور، scopeهای مقصد، مذاکرهٔ capability نسخهٔ ۱، تمدید نشست، چرخش کلید و وضعیت سلامت در فاز ۰۲ افزوده شده‌اند؛ تست واقعی دو VPS همچنان لازم است.
- **پلتفرم اپ:** فازهای ۰۳ تا ۱۳ Registry مالکیت، Deploy پایدار، Runtime، Runnerهای Laravel/Node، انتشار Static/SSR، منابع و پایش را پوشش می‌دهند. فازهای ۱۴ تا ۴۸ در حال اجرا یا برنامه‌ریزی‌اند و مرز واقعی پیاده‌سازی آن‌ها در [وضعیت نقشه‌راه](app-platform-roadmap-18-48.md) آمده است؛ شبکه، انتقال و ناوگان چند VPS همچنان به پیاده‌سازی و تست واقعی چندمیزبانه نیاز دارند.
- **CI:** GitHub Actions برای CI و انتشار مستندات وجود دارد. دستورهای تست محلی در `docs/en/development.md` ثبت شده‌اند.
- **نسخه‌بندی:** نسخه‌های Rust و Frontend هماهنگ‌اند؛ ابزارهای پایدار و prerelease به‌ترتیب `scripts/bump-version.sh`، `scripts/bump-development-version.sh` و `scripts/check-versioning.sh` هستند.

## مواردی که پیش از پیاده‌سازی باید دوباره تصمیم‌گیری شوند

۱. Runner اولیه با systemd بومی، Container یا adapter قابل انتخاب ساخته شود؟ سطح ایزوله‌سازی را نباید بیشتر از مرز اجرای واقعی وعده داد.
۲. سایت‌های Nginx و Containerهای موجود چگونه کشف، وارد Application و از مالکیت تکراری محافظت می‌شوند؟
۳. rotation نشست و credential چطور pairing فعلی را بدون قطع دسترسی یا باقی‌ماندن نشست بلندمدت مهاجرت می‌دهد؟
۴. اولین محیط انتشار دقیقاً کدام نسخه‌های Ubuntu/Debian و معماری و حداقل RAM/دیسک را پشتیبانی می‌کند؟ دسترسی بسته‌ها میان نسخه‌ها متفاوت است.
۵. کدام نوع داده با rollback آزمایش‌شده قابل انتقال است و کدام نیاز به downtime یا رفتار best-effort دارد؟
